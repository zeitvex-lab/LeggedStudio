# Legged Studio 项目价值观

> **版本**：1.0 ｜ **日期**：2026-09-13 ｜ **产品版本**：0.55.38（**已纳入 `tools/doc_reality_check.py` 锚点**，改这里必须与 `VERSION` 一致）
> **性质**：**本仓库的最高裁决依据**。所有方案、评审、重构、取舍，最终都要回到这份文件。
> **与其它文档的关系**：`最终愿景.md` 说「做成什么样」，`重构方案` 说「怎么落地」，本文件说「**为什么这么选、冲突时谁优先**」。

## 0. 一句话

> **让一台腿足机器人从 URDF 到实机，每一步都数值可追溯、证据可复核、结论可复现——并且这件事不要求使用者懂命令行。**

## 1. 十条价值观

### V1 · 可追溯优先于功能多（Traceability first）

**主张**：任一策略都能回溯到 `契约 hash + 归一化器 hash + recipe 版本 + seed + 评测报告`。宁可少一个算法，不少一条证据链。

**为什么**：机器人 RL 的失败绝大多数**不是「训不出来」，而是「不知道为什么这次不一样」**。没有谱系的产物，等于一次性的运气。

**落到代码**：`policy-artifact` 携带 `trained_against`；`export_gate` DENYLIST；`runs/<id>/resolved-config.json` + `environment-lock.json`；部署包附「人工确认清单」。

**反面**：只存在 `policy.onnx` 而不知道它对齐哪份契约的「孤儿策略」——**必须撤下**（规则 S 已如此执行）。

---

### V2 · 单一事实源，其余皆为可再生的派生视图（Single Source of Truth）

**主张**：同一个物理事实**只允许在一处出现**。其它位置的重复，必须是「可再生成 + CI 漂移检查」的派生视图，不允许双写。

**为什么**：`contract.json` (v2) + `contract_v3.json` + `simulation/config.json` 三处各写一份 PD/armature 时，**没有人知道哪份是对的**——最后是「两边都写错就一直错」。

**落到代码**：契约 v3 为唯一入口，v2 由生成器派生；`tools/generate_contract_models.py` 参与 CI 漂移检查；**待办**：`simulation/config.json` 降级为引用（B3 剩余项）。

**判据**：新增一个字段时，如果需要在两处同时维护——**设计就是错的**。

---

### V3 · 差异数据化，共性代码化（Data over Code）

**主张**：机器人之间、任务之间的差异，全部下沉为 **JSON/YAML 数据**；共性逻辑上移到共享层。资源文件里**不放代码**。

**为什么**：`assets/robots/<id>/training/source/` 塞进一整棵训练源码树（181 个 py）后，新增一台机器人的成本是「复制 200 个文件」，且 go2 包里会混进 g1 的代码。

**落到代码**：`contracts/` 零依赖 schema；`registry/skills/*.json` + `registry/rewards/*.json`；`profiles/*.patch.json` 只写差异；算法实现属 adapter runner，用 `runner_ref` 引用。

**判据**：**「新增一台机器人 = 1 目录 + 3 JSON + 模型文件」**（DoD #2）。做不到，就是共性没有上移干净。

---

### V4 · 契约即宪法，不合即拒（Contracts are Law, Fail-Closed）

**主张**：接口对不上就**拒绝**，不猜、不补、不静默降级。缺失必须**显式报错**。

**为什么**：跨后端/跨部署的 bug，50% 以上是「观测组、action scale、关节序、归一化」的不一致——它们**不会崩，只会静默地变差**，而静默的变差最难查。

**落到代码**：`export_gate` 双 gate（dummy forward 维度 + 固定输入数值回放 <1e-5）；DENYLIST 语义；缺失字段在 verify 阶段 fail-closed；**待办**：把「字段不对称出现」也纳入 fail-closed（借 UniLab `ENV_STRUCTURAL_DENYLIST` 的做法）。

**判据**：**「能力缺失时报错，而不是回退」**。默认不支持，显式开启。

---

### V5 · 分层隔离，边界不可越（Layered Isolation）

**主张**：四层严格单向：`contracts`（零依赖）→ 控制面（永不 import Torch）→ 训练 adapter（隔离 venv 子进程）→ 浏览器 WASM / 服务端 MuJoCo。**跨层问题在 owner 层修**。

**为什么**：训练栈崩溃不能带走工作台；控制面一旦 import torch，桌面程序就再也不可能「双击即用」。

**落到代码**：`adapters/backend_adapter.py` 的 `BackendAdapter` Protocol；训练跑在隔离子进程；`contracts/` 无第三方依赖。

**判据**：改一个 bug 时，先问「**这个契约属于谁**」，再决定改哪一层——**不允许在脚本层打补丁掩盖**。

---

### V6 · 证据等级发言，不说空头承诺（Evidence-Graded Claims）

**主张**：所有「支持 / 已完成 / 可用」的话，都要挂证据等级：**Registered → Configured → Tested → Benchmarked → Recommended**。没有仓库内证据，不得声称稳定支持。

**为什么**：`00_resources` 里 83 个项目，绝大多数只有**目录存在**（L1/L2）；把「目录存在」说成「可用」，会让整份文档失去可信度。

**落到代码**：`00_know` 报告必须带**日期 + 证据来源**；任务清单状态按**实测**标注（已完成 / 部分完成 / 未动）；`本次实测` 与 `继承标注` 要能区分。

**判据**：**「已含 / 已具备 ≠ 已验证可运行」**——这句话应写进每一份盘点的开头。

---

### V7 · 零命令行，把复杂度关起来（Zero-CLI for the User）

**主张**：面向使用者的路径是**双击 → 启动 → 干活**。命令行是工程师的入口（CLI），不是使用者的门槛。

**为什么**：这是本产品区别于「一堆 python 脚本 + 配置文件」的核心差异点。

**落到代码**：Electron 壳负责运行时供应 + 后端生命周期 + 系统集成；Web 无构建、刷新即生效；环境页 L0–L6 分层体检给出**中文原因 + 怎么办**；`onboard` 是新机器人**唯一必需的人工介入点**。

**判据**：一条新流程如果需要用户「先 pip install 再改 yaml」——**不算完成**。

---

### V8 · 减法优先，瘦身是功能（Subtraction is a Feature）

**主张**：删掉一份重复的 mesh、一条无训练源码的策略、一个隐式契约，**与新增一个功能同等重要**。

**为什么**：`assets/robots` 从 639.7 MB 降到 424.7 MB 的过程中，**没有加任何能力，但整个仓库的开发体验变了**。臃肿会以「每次要多想一层」的方式持续收税。

**落到代码**：mesh 单副本；`audit_porting_admission` 的规则 C/X；`git ls-files "*.pyc"` 恒为空；孤儿资产清理。

**判据**：**做任何重构时，先找「可以删掉什么」，再找「要加什么」。**

---

### V9 · 只读优先，改动即出新版本（Read-Only Kernels, Immutable Artifacts）

**主张**：事实内核只读 + 版本化（一改就出新 hash，不就地覆盖）；产物不可变 + 引用 + hash；配方 base + override patch。

**为什么**：可复现的前提是「同一份输入永远指向同一个东西」。就地覆盖意味着**历史结论不可复核**。

**落到代码**：contract v3 改动产出新 `contract_hash`；`runs/<run-id>/` 不可变；`registry/skills` 的 extends 链深合并；包内引用一律相对路径 + sha256。

**判据**：**「改任何东西 = 派生新对象，不就地覆盖」**。

---

### V10 · 结论要留下「被否决的方案」（Record What We Rejected）

**主张**：每一份重要决策，除了写「选了 A 和为什么」，还要写「**为什么不选 B/C/D**」。

**为什么**：这是本仓库**当前最缺的一条**。`00_know` 有大量「结论 + 证据」的报告，但**几乎没有「替代方案与否决理由」**——于是同一个问题过几个月会被重新提出、重新论证、可能得出相反的结论，然后再次反转。**UniLab 的 6 篇 ADR 全部带 `Alternatives Considered`，这是它工程性最强的部分。**

**落到代码**：决策类文档统一模板：

```
Context            背景与约束
Decision           选了什么
Stable Contracts   哪些是不可动的契约
Consequences       后果（含「不做什么」）
Alternatives       被否决的方案 + 否决理由   ← 必须写
Evidence In Repo   代码/文档里的证据位置
```

**判据**：**没有 `Alternatives` 的决策文档，不算决策文档。**

## 2. 冲突时的优先级（裁决序）

当价值观互相冲突时，**按序号裁决（小号优先）**：

```
V1 可追溯  >  V4 契约  >  V5 分层  >  V3 差异数据化  >  V2 单一事实源
          >  V9 只读版本化  >  V8 减法  >  V6 证据等级  >  V7 零命令行  >  V10 留存否决
```

**几条最常见的冲突与裁决**：

| 冲突 | 裁决 | 理由 |
|---|---|---|
| 「快速加个功能」 vs 「先把契约定清楚」 | **先定契约**（V4 > 功能） | 契约错一次，后面所有产物都要重做 |
| 「多后端支持」 vs 「保持简单」 | **先做能力契约，后端后置**（V4+V5 > V8） | 能力声明是公共前置，引擎是可插拔实现 |
| 「文档写全一点」 vs 「代码里有就行」 | **文档只写「为什么」，代码写「是什么」**（V2 + V8） | 双写必然漂移 |
| 「兼容旧格式」 vs 「直接改掉」 | **派生兼容视图 + 漂移检查**（V2 + V9） | 不破坏别人，也不双写 |
| 「报错太丑，静默回退吧」 | **绝不允许**（V4 > 一切体验） | 静默降级是本项目历史上最贵的一类 bug |
| 「这个结论先不写否决理由了」 | **必须写**（V10） | 不写，就会被重新争论一遍 |
| 「先加能力再说，瘦身以后做」 | **先减后加**（V8） | 复杂度是复利，越晚还越贵 |

## 3. 反面清单（本项目明令禁止的事）

| # | 禁止 | 依据 |
|---|---|---|
| N1 | 在多个位置重复维护同一物理事实 | V2 |
| N2 | 资源文件（JSON/YAML/契约）里内联代码 | V3 |
| N3 | 契约不一致时静默降级 / 回退默认值 | V4 |
| N4 | 控制面 import torch / 训练栈 | V5 |
| N5 | 未经实测就声称「已完成 / 支持」 | V6 |
| N6 | 把「需要手改配置」当作交付完成 | V7 |
| N7 | 资源文件入库产物（`.pyc` / 训练 checkpoint / 日志） | V8 |
| N8 | 就地覆盖已有契约或产物 | V9 |
| N9 | 决策文档只写「选了 A」，不写「为什么不选 B」 | V10 |
| N10 | 把其他机型的资产/代码塞进本机型包（包边界泄漏） | V3+V8 |

## 4. 这份价值观怎么用

1. **写方案前**：对照 V1–V10，确认方案不违反任何一条反面清单（§3）。
2. **评审 PR 时**：先问「这动了哪个契约」（V4/V5），再问「这是不是可以删掉的东西」（V8），最后问「结论有没有留下否决理由」（V10）。
3. **做取舍时**：按 §2 的裁决序，不要凭感觉选。
4. **写完决策文档时**：检查是否包含 `Alternatives Considered`；没有就不算完成（V10）。

> **本文件的维护约定**：价值观**不轻易改**。若要修改，必须新开一节写明「改了什么、为什么旧表述不够用、影响了哪些既有结论」，**保留修改链**（与 V9、V10 一致）。
