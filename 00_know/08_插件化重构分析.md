# 08 · 插件化重构分析（对照 deepseek-harness「一切皆插件」）

> **版本**：1.0 ｜ **日期**：2026-10-02 ｜ **性质**：分析裁决文档（动代码前先裁决）
> **对照源**：`00_open/deepseek-harness`（DeepSeek 官方 agent harness，Cordis IoC 框架之上的一切皆插件架构；其 docs/architecture.md 自述 "There is no privileged core to patch"）
> **本文回答**：它那套架构搬多少、怎么搬、不搬什么、按什么顺序搬——对齐本仓四轴模型（`06` §0.4），不动已验证的骨架。

---

## 0. 结论先行（一段话）

**本仓与 dsh 的目标不同，但"组合机制"高度同构——不需要重写，需要的是把本仓已经自发长出的 9 张注册表收进 dsh 式的统一插件协议（entry 树 + 分层 patch + inject 声明），并消灭残余的 4 处硬编码分发点。** 本仓的"插件"天然是**数据**（registry JSON + Kit 数据类），dsh 的插件是**代码**（函数+静态字段）——这正是因为训练流水线的扩展维是机型/地形/奖励/算法（全是数据可表达的），而 dsh 的扩展维是能力（工具/模型适配器，必须代码）。**搬它的"组合与装配协议"，不搬它的"一切皆代码插件"**。

---

## 1. 两侧架构对位（先看清同构与差异）

| 维度 | deepseek-harness | 本仓现状 | 同构度 |
|---|---|---|---|
| 插件单元 | `(ctx, config) => disposer`，元数据=导出静态字段 | **数据档案**：profile JSON（entrypoints: env/runner/runner_class）+ Kit 数据类（VelocityProfile/LegsOnlyRecipe）+ 契约 | **高**（本仓 entrypoints ≈ dsh entry 的 name+config；Kit dataclass ≈ dsh Config schema） |
| 注册表 | `Map<Function, Runtime>`（运行时） | **registry/ 9 张表**：families(skill_catalog)/terrains/skills/tasks/task_plugins/rewards/motions/packs/perception_providers（全部显式 index + schema_version） | **高**（本仓甚至更声明式——表驱动而非码驱动） |
| 组合格式 | cordis.yml entry 树 + bundle/profile/home 四层 patch（id 定位、后写胜） | 训练 = contract(profile_id) → effective-config（**单次快照**，无层叠）；任务 = task-profiles 组装（地图×控制器×执行器） | **中**（有组合、无层叠 patch——见 §3-G1） |
| 依赖表达 | `inject: ['tools','sessionProjections']`（服务定位，加载序=可用性驱动） | 无显式依赖：装配顺序 = 调用链硬编码（builder 里 if family → kit） | **低**（见 §3-G2，本仓最大差距） |
| 可逆性 | 一切注册是 effect（disposer 逆序），isolate 支持同服务多实现 | 无运行时挂载概念（装配=一次性构造 env cfg）——**训练域天然不需要热插拔** | 不适用（见 §4 不搬） |
| 配置校验 | schemastery 启动即校验、fail-loud | pydantic/契约校验器 + doc_reality_check 16 锚点 + 冒烟门——**已是 fail-loud 体系** | **高** |
| 扩展点 | register() API + 类型化事件（waterfall/emit） | 族 Kit 工厂函数签名（make_env_cfg(binding, profile, variant)）；skill_catalog 声明 entrypoint | **高**（工厂签名 ≈ register API 的静态版） |
| 产物契约 | 无此概念（不产出模型） | **五层保真链 + emit_assembly**（导出时刻机械产出部署契约） | 本仓独有、**比 dsh 多的东西** |
| 版本兼容 | peer semver + 豁免登记；数据格式 version+迁移链 | schema_version 逐表声明；contracts v2/v3 迁移先例 | **中高** |

**关键判断**：本仓不是"没插件化"，是**插件化在数据层早已完成**（9 张表+两族 Kit+契约导出），缺的是 dsh 那套**把插件组装成产品的协议层**（entry 树/patch/inject/审计）。

## 2. dsh 可移植的架构决策（按对本仓价值排序）

1. **entry 树 + 分层 patch（组合协议）**——价值最高。训练配置 = 一棵 entry 树（机型包 × 配方 × 地形 × 算法 × 规模），四层 patch（族基线 → 机型包 → 档案 → CLI overlay）按 id 定位、后写胜。本仓现状是"档案 = 全量快照"——想跑一个"rough 地形 + lainlab 奖励 + PPO"的组合必须新建整档案；patch 化后 = 基线 + 3 行覆盖。
2. **inject 声明式依赖**——消灭硬编码分发。skill_catalog 的 env entrypoint 声明 `inject: ['terrain', 'reward_profile', 'runner']`，装配器按可用性解析而非 if family 分支（§3-G2 的 4 处硬编码全部消失）。
3. **Capability seam 三角色**（定义包/实现包/消费包）——本仓的族 Kit 已是此形态（binding=定义、kit config=实现、包侧 profile=消费），把它**升格为显式命名规范**并生成 seam 图（dsh 的 gen-doc-graphs 先例）。
4. **启动审计 + fail-loud**——`requiredStartupEntryIds` 先例：装配前审计"必需 entry 全在且版本兼容"，缺 = 拒装配。本仓的契约哈希门/冒烟闸已是这个形态，把它统一进装配协议。
5. **配置目录生成**（doc 即派生物）——dsh 的 gen-config-catalog 从源码 schema 生成配置目录并有 doc-sync 门禁。本仓 04_参数真值标准 手写 ↔ emit_assembly 机械导出——**对齐方向：04 的人写表格逐步换成 emit 产物**。

## 3. 差距清单（G=Gap，按修复价值排序）

### G1 · 组合无层叠（最大差距，直接锁死实验吞吐）
- **现状**：`training/profiles/*.json` 是全量快照（55 份档案大量复制粘贴；"flat+stairs"要新档案）。
- **dsh 解法**：entry 树 + id 定位 patch。
- **迁移**：profiles.json 增加 `"extends": "<base_profile_id>"` + `"overrides": {...}`（浅合并、数组整体替换、冲突 fail-loud 报路径）；effective-config 生成链不变（解析期展开成全量再走既有装配）。**向后兼容**：无 extends 的档案 = 现状原样。
- **风险**：低（纯解析层，装配与门禁不动）；冒烟闸自动覆盖（指纹含解析产物）。

### G2 · 硬编码分发点（4 处，是"新族要改核心"的根因）
- `family_skill_builder.py:36-42`：FAMILIES 字典写死两族 → kit 路径（**这恰是 dsh "privileged core" 的反面教材**：新族=改核心文件）。
- `family_skill_builder.py:99`：`from .kits.quadruped_kit.skills import family`（绑定解析也写死 quadruped 视角）。
- `policy_acceptance.py:1134 FRAME_BUILDERS`：24 个 kind 手工注册表（虽然观测布局声明化在收窄它）。
- `export_checkpoint_onnx.py` 曾硬编码 legs-only 入口（已修为档案动态解析——**这就是 G2 类缺陷的既成先例**）。
- **迁移**：FAMILIES 字典下沉进 `registry/families/index.json`（族注册表自描述 kit 路径与 binding 工厂）；FRAME_BUILDERS 冻结不再新增（布局声明化 + assembly 段表接管，wrap 语义进段词汇表后零 builder）。

### G3 · 插件间无事件通道（策略/拦截类扩展无处安放）
- **现状**：想加"训练中期评估探针""reward 异常熔断"这类横切能力只能改 native_worker 主循环。
- **dsh 解法**：类型化事件（waterfall 可短路）。
- **迁移**（小 Python 版，不上框架）：native_worker 训练循环暴露 3 个钩子位（`on_iteration_end / on_checkpoint / on_terminal`），档案可声明 `hooks: [{at: on_iteration_end, call: tools.trend_probe, every: 250}]`——趋势探针从"训后手工跑"变成"训中自动跑"。
- **风险**：中（动主循环）；先落 on_checkpoint 一个位验证。

### G4 · 版本豁免机制缺失
- 本仓 schema_version 有、但"旧档案跑在新装配器上"没有兼容评估。dsh 的 `evaluatePluginCompatibility`（只读 manifest 不 import 代码）+ 豁免登记可直接套在档案上。

### 非差距（本仓已领先的部分，别倒退）
- 五层保真链（mjcf/环境/配方/管线/测量）——dsh 无对应物；
- emit_assembly 契约导出——dsh 的配置 schema 生成只管自身配置，不管"产物如何被另一个运行时消费"；
- 9 张 registry 表的显式 index + fail-closed——比 dsh 的运行时注册表更可审计。

## 4. 明确不搬什么（裁决）

| 不搬 | 理由 |
|---|---|
| **Cordis/IoC 容器本身**（Context/Fiber/Service/Registry 运行时） | 训练装配是**一次性构造**（build env cfg → 训完即弃），没有热插拔/并发隔离需求；引入运行时容器 = 为不存在的需求付复杂度。dsh 需要它是因为 agent 会话要动态装卸工具。 |
| **一切皆代码插件** | 本仓插件天然是数据（四轴全可数据表达）；把 profile JSON 改成 Python 插件是**倒退**（丢掉声明式的全部好处：可 diff/可审计/机器可验）。 |
| **事件总线全量（5 分发模式/scope 链）** | 只搬 G3 的 3 个钩子位；parallel/bail/scope 过设计。 |
| **HMR/热重载** | 训练进程不需要。 |
| **dsh 的包管理/plugin-manager（npm 安装面）** | 本仓"安装插件"= 放一个机器人包目录 + registry 登记，已有 onboard 双入口，无需 npm 面。 |

## 5. 迁移路径（三步，每步独立可交付、可回退）

**Step 1 · 档案层叠（G1，~1 天）**：`extends/overrides` 进 profile 解析链 + 装配器不变 + 冒烟闸验证解析等价。收益：组合实验从"新建全量档案"变"3 行覆盖"，55 份存量档案可逐步收敛到基线+变体树。
**Step 2 · 族注册表自描述（G2，~半天）**：FAMILIES 字典 → `registry/families/index.json`；family_skill_builder 只读表。收益：新族零核心改动（数据进去就能装配），与 dsh "no privileged core" 对齐。
**Step 3 · 训练钩子位（G3，~1 天）**：on_checkpoint 钩子 + trend_probe 首个消费者。收益：趋势判据进训练循环（每 250 轮自动评测，判负自动早停可期），人工法证循环进一步消失。

**不做大爆炸**：三步各自带测试独立合入；每步后跑全量后端测试 + 冒烟 + doc 门禁。emit_assembly/五层保真链/四轴模型完全不动。

---

## 6. 对四轴模型的反哺

插件协议层落地后，四轴的表述升级：**机型=契约插件 / 地形=课程插件 / 奖励=配方插件 / 算法=变体插件 / 任务=组合插件**——每轴一个 registry 表 + 一个 patch 维度；"技能=组合点"从概念变成 entry 树上的一个节点路径。`06` §0.4 在 Step 1-3 完成后补一节"组合协议"，本文归档为它的依据。
