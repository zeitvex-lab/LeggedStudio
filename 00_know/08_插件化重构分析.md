## 0. 裁决摘要（3 分钟读完）

1. **本仓"一切皆插件"今天是口号，不是机制。** 全仓存在 **6 套互不相通的"插件"机制**、**3 种 schema 声明风格**（18/13/1，实测）、31 条内联路由；插件内核 `plugins/core.py`（168 行）**零生产消费**——唯一 import 方是它自己的测试（`backend/test_plugin_core.py:13`）。
2. **硬编码主战场不在 backend（约 48 行级），在产品面与装配面**：`backend/api_complete.py`（1009 行）的 31 条内联路由、`web/` 12 页（最大单页 179 KB）、`backend/policy_artifacts.py:72-87` 的 `(robot_id, obs_dim)→builder` 硬表、`adapters/mjlab/kits/__init__.py:5-8` 写在 docstring 里的 Kit 归属表。
3. **上游 dsh（deepseek-harness）证明"一切皆插件"可以成立**，靠三样本仓没有的东西：单一服务上下文（`ctx.<key>` + `inject` 依赖驱动装载顺序）、patch 整行替换的组合层（bundle/profile/patch 三层）、把"新行为去哪"做成机器生成的 seam 图。**抄协议语义与纪律，不抄它的 TS 技术栈**（§5.5 候选 A 否决）。
4. **定位重审**：7 个竞品全部落在"单点深度"或"链路宽度"，**"宽度 × 可信可复核"象限没人占**。定位从"全链路工作台"收敛为**"策略配方工厂 + 可信试玩场"**（§3）。
5. **功能缺口按竞品反推五条**（§6.2）：动作/模仿工具链（BC·DAgger）、零训练上手、多技能单策略与起身任务、厂商适配包入口、离线工程格式。**明确不做**四条（§6.3）。

### 2.3 LainLab 源码级解剖（最直接的同类）

**三个可抄**：

1. **工具链补链**：`src/toolchain/{calibrate,collect,bc,dagger,evaluate,export}.py`——**BC 与 DAgger 是本仓完全没有的一段**（本仓 imitation 只到 AMP/CTS/TS 蒸馏，缺"从参考动作到可部署策略"的离线模仿路径）。这是竞品证据里**唯一我们缺的实链路**。
2. **基线随包分发**：`src/baseline/opendoge/skills/baseline.json` + `baselines.py` 发现机制——训练产物成为一等资产，工作台直接列出。本仓 `tools/baselines/*.json` 是门禁基线，不是**产品基线**（用户可一键试玩的参考策略）。
3. **任务类型即目录**：`src/tasks/{velocity,tracking,getup,handstand,jump,multiskill,amp}`——**getup（起身）与 multiskill（单策略多技能）是本仓没有的任务类型**。

**一个反例（价值最大的发现）**：`src/workbench/catalog.py` 用**硬编码 Python 字典**表达任务目录——`TASKS`（11 条字符串）、`TASK_ASSETS`（13 条路径）、`SKILLS`（9 条）、`ALGORITHMS`。注释明确写"importing the workbench never imports torch"（纪律同本仓控制面），但**加一个任务 = 改 dict + 改 robots 注册 + 改 skills 表，三处手工同步**。这正是 `01` §五"差异由数据表达"要消灭的形态——**LainLab 证明市场上没有第二个"注册表驱动 + 机器可查"的同类**。本仓 `registry/` 20 个子域是既成差异化资产，插件化重构是把它们从"一堆 JSON"升级为"一套协议"。

## 3. 新项目定位（提案，待并入 `01`）

### 3.1 原定位的四个失效点（对照 §2 证据）

| 原表述 | 失效原因 | 证据 |
|---|---|---|
| "从模型到实机的整条链路收进一个产品" | 链路各段都有更深的竞品：模型段（StackForce）、训练段（1000frames）、动作段（RoboCraft/LainLab）、部署段（DimOS/RoboCraft）。**全链路每段都做 = 每段都不够深** | §2.2 |
| "使用者不需要懂命令行" | 兑现方式被重定义：1000frames 第一入口是**加载已训 ONNX 直接试**（零配置零训练）；本仓第一入口仍是"建训练任务"，在链路中段 | §2.2 |
| "先自用后开源" | 掩盖了产品事实：**"包"才是第三方参与的最小单位**，而"包"没有协议（6 套机制） | §1.2 |
| 3–6 月锚点=两族八机收口 + v1.0 | 八机收口依赖统一训练架构（06 §0.4），其边际成本问题**就是**插件化问题——两者是同一件事两面，锚点应合并表述 | 06 §0.4 |

### 3.2 新定位

**一句话**：**腿足机器人策略的配方工厂与可信试玩场**——机型×技能×地形×判据全部声明式组合，改配置不改代码；每个策略零训练可试、加载即验章，产物带着证据链上机。

**四轴修订**（对齐 `01` 裁决块格式）：

| 轴 | 原裁决（2026-09-28） | 修订提案 | 依据 |
|---|---|---|---|
| 主叙事 | 全链路工作台 | **配方工厂 + 可信试玩**两段收拢：配方段（资产→契约→训练→产物）做深，试玩段（零训练上手→浏览器 sim2sim→判据）做顺；部署降级为"包生成+平台适配"，不再是主叙事一段 | §3.1 表 1 |
| 第一用户 | 自己/本团队 | 维持，**追加 dogfood 指标**：本团队每月经产品完成的"新机型/新技能/新面板"次数是"改得动"的真值——竞品没有这个闭环 | `01` §二 |
| 生态姿态 | 先自用后开源 | **"包即插件"提前为主张**：开源 v1.0 交付物不是代码，是**插件协议+校验门+若干示范包**；第三方贡献最小单位 = 一个过校验的 `plugin.json` 包 | §1.2 |

## 4. 目标架构：一切即插件

### 4.1 一页图

```
  registry/plugin-registry.json                ← 唯一装配清单（6 套旧机制的全集收敛点）
        │ ①加载 ②schema 校验 ③拓扑排序（requires 驱动，不写死 boot 顺序）
        ▼
  plugins/runtime.py（内核，≤400 行，零业务零机型 id）
        ├─ 服务上下文：ctx.provide(key, value) / ctx.get(key) / ctx.try_get(key)
        ├─ 事件五模式：emit / waterfall / parallel / serial / bail
        └─ patch：按 id 整行替换或插入（不 merge——防半覆盖静默漂移）
        │
        ├─ 消费投影①产品面：面板导航 / HTTP 端点 / CLI 子命令 / 桌面可见性（四投影）
        ├─ 消费投影②装配面：族 Kit / 技能 / 地形 / 奖励 / 算法（训练 worker 侧）
        ├─ 消费投影③验证面：插件自带 verify → 门禁事件（30 个 audit 脚本归位）
        └─ 消费投影④生态面：第三方包过 manifest 校验进索引（"包即插件"）
```

### 4.2 内核三原语（cordis 语义 / Python 实现，文件 `plugins/runtime.py`）

| 原语 | API | dsh 对应 | 本仓适配说明 |
|---|---|---|---|
| **服务上下文** | `ctx.provide(key, value) -> disposer`；`ctx.get(key)`（缺即抛，列出可用）；`ctx.try_get(key)` | `ctx.<key>` 服务声明 + `inject` | **装载顺序由 requires 可用性驱动（拓扑排序）**，取代 6 处手写 boot 顺序；注册即 effect，`ctx.dispose()` 逆序回滚 |
| **事件** | `ctx.on(event, fn)` / `ctx.emit|waterfall|parallel|serial|bail(event, ...)` | 5 dispatch modes | emit=观察；waterfall=中间件（契约完备性封口这类横切）；bail=首票否决（部署 gate）；**不引 fiber/async**（训练装配一次性同步，异步无意义——否决理由） |
| **patch** | `apply_patch(base, patch)`：id 命中=**整行替换**，未命中=插入，后写胜 | bundle/profile/patch 三层 | 层叠来源：插件基线→族→机型包→档案→CLI；**整行替换而非 merge 是有意取舍**（dsh 原注释：merge 产生"半覆盖"，正是本仓 0.35/0.5 缩放事故的同一类病） |

**内核硬约束**：≤400 行；不 import 本仓任何模块；不出现机型/族/功能 id（门禁 `test_kernel_purity.py` AST 扫描）。现 `plugins/core.py` 的 Seam 桶升级为服务上下文，`Entry` 保留为装载行单元。

### 4.3 插件清单 `plugin.json`（统一 schema，取代 3 种风格）

```json
{
  "schema": "legged-plugin-1.0",
  "id": "skill.quadruped.velocity",
  "kind": "skill",                    // 冻结清单：robot|family|skill|terrain|reward|algorithm|
                                      // task|sensor|evaluator|panel|controller|pack|profile
  "provides": ["skill:velocity", "obs_layout:quadruped_45"],
  "requires": ["robot:any", "terrain:any"],
  "provenance": { "upstream": "...", "evidence": ["00_resources/..."], "license": "MIT" },
  "surfaces": {                       // 四投影（缺省即不可用=诚实禁用，不静默隐藏）
    "panel":   { "title": "速度跟踪", "group": "训练", "order": 30, "desktop": true },
    "http":    { "method": "POST", "path": "/api/skills/velocity/train" },
    "cli":     { "command": "train velocity" },
    "desktop": { "visible": true }
  },
  "impl": {                           // 双侧投影（§4.5）
    "control_plane": "backend/skills/velocity.py:build",   // 零 torch 可 import
    "runtime":       "adapters/mjlab/kits/quadruped_kit/skills/velocity:VelocityEnvCfg"
  },
  "verify": [                         // 插件自带验收（§4.6）
    { "id": "assembly",  "tool": "tools/validate_family_skill_assembly.py", "args": ["--skill", "{id}"] },
    { "id": "trainable", "tool": "backend/trainability_check.py",             "args": ["--skill", "{id}", "--iters", "1"] }
  ]
}
```

**13 个 seam（冻结清单）**：`robot / family / skill / terrain / reward / algorithm / task / sensor / evaluator / panel / controller / pack / profile`——与 `registry/` 现有 20 个子域**一一映射**（多对一收敛，如 rewards+skills/patches→reward、packs+task_plugins→pack）。

### 4.4 四投影：面板插件的真实形态

迁移后一个"页面/面板"声明带来四份产物，全部由 `plugin-registry` 生成、**零手写路由/导航**：

| 投影 | 生成物 | 取代 |
|---|---|---|
| 导航 | topnav/侧栏/桌面 launcher 的导航数组（JSON 下发） | `web/shared/topnav.js` 手写清单 + `panel_registry.render_navigation` |
| HTTP | FastAPI 路由（从 `surfaces.http` 挂载，provider 走真 `module:attr` importlib） | `api_complete.py` 的 31 条内联路由中可归属单域的部分 |
| CLI | argparse 子命令表 | `cli_panels.py` 的 `globals().get` 假解析 |
| 桌面 | `desktop.visible` 过滤 + capability 裁剪 | electron launcher 静态清单 |

**诚实禁用**：`requires.services`（如 backend/训练栈/GPU）探测不可用 → 置灰+原因原文，永不静默隐藏。

### 4.5 双侧投影纪律（与"控制面永不 import 训练栈"的和解）

dsh 是单进程 TS 无此问题；本仓必须显式设计：

- **`impl.control_plane`**：零 torch 可 import（加载、校验、投影、目录）——**门禁**：`test_impl_importability.py` 在无训练栈环境 import 全部 control_plane provider；
- **`impl.runtime`**：只在 worker 子进程 import（env cfg / 算法类 / 评测器）；
- 两份 impl 由**同一个 `plugin.json` 声明**——协议唯一，投影两侧（这是与"6 套机制"的根本区别：dsh 的 `packages/api` 声明与 `packages/extensions` 实现分离思想的 Python 版）。

### 4.6 验证器事件化（30 个 audit/validate 归位）

- 插件声明 `verify[]`，`tools/audit_plugin_verify.py` 扫描全部 manifest 生成门禁清单（**新增能力=加插件，不改 CI 脚本清单**——dsh "Where new behavior goes" 表的本仓等价物）；
- 现有 30 个脚本**不重写**，只改发现方式：从"手维护在 .cnb.yml"改为"从 manifest 派生"；
- 全站级横切（doc_reality_check、obs_crosscheck 全量）保留为**内核事件**（waterfall 模式）。

### 4.7 seam 图（机器生成，进 CI）

`tools/gen_capability_seams.py` 从 manifest 生成 `docs/capability-seams.md` 等价物：每个 seam 的提供者/消费者/覆盖矩阵 + **"新增一个 X 该挂哪"表**。这是"框架零特判"从 grep 纪律升级为**机器可查结构**的门。

## 5. 技术方案选择：四个候选与否决理由

| 候选 | 内容 | 否决/采纳理由 |
|---|---|---|
| **A** | vendor Cordis（TS 插件框架），前端/桌面全迁 TS + pnpm | **否决**：① web/ 是无构建纯静态（136 文件）且离线包以 `web/sim2sim/` 为根——迁构建链=动离线形态，06 §3.1 已裁决不动；② backend 是 Python 控制面，cordis 的 ctx 服务模型无法跨语言；③ 迁移成本 >> 收益（协议语义可抄，技术栈不可抄） |
| **B ★** | **单一插件协议**：cordis 语义 + Python 实现（§4.2 三原语），registry/ 收敛为 `plugin.json`，13 seam | **采纳**：① 保留 web 无构建与四层隔离两条既有裁决；② 死内核 `plugins/core.py` 升级即用，不推翻；③ 与 `adapters/mjlab` 隔离 venv 兼容（双侧投影 §4.5） |
| **C** | 只统一数据注册表（schema 归一 + 总表），不动协议 | **作为 Phase 0 吸收**：它独立可交付、可回滚、零行为漂移；但只做 C 则"一切即插件"停在"一切皆数据"，31 条内联路由与假 module:attr 原样保留——不解决问题，只铺路 |
| **D** | 照搬 dsh monorepo tier 物理重排（packages/* + bundles/* + apps/*） | **否决**：① 路径硬依赖极重（doc_reality_check 16 锚点、registry evidence 字段路径、包 stub 沿目录自举、测试 docstring 行号引用）；② tier 是**逻辑概念**（内核/域插件/组合层/投影），物理路径不搬家也能成立——用 manifest 表达 tier，不用目录表达 |

### 5.5 裁决表

| 维度 | 选择 | 依据 |
|---|---|---|
| 内核语言 | Python（`plugins/runtime.py` ≤400 行） | 控制面同语言；训练面已是 Python |
| 前端 | 保持无构建 ES module + JSON 投影 | 离线包结构不动（06 §3.1 裁决） |
| 装配语义 | 服务上下文 + requires 拓扑 + patch 整行替换 | dsh 验证过的三件套；同步一次性，**不要 fiber/HMR** |
| manifest 格式 | JSON（`legged-plugin-1.0`） | 与 contracts/ Schema 体系一致，可生成 Pydantic |
| 旧机制 | 6 套逐 Phase 并入（§7 映射表），每 Phase 机器计数单调减少 | 防"改了一半" |

## 8. 不变式与门禁（全 Phase 有效）

1. **控制面永不 import 训练栈**：`impl.control_plane` 全量在无 torch 环境 import 成功（`test_impl_importability.py`）——插件化不得破坏四层隔离。
2. **内核 ≤400 行零业务**：AST 门禁，机型/族/功能 id 出现即红。
3. **patch 整行替换**：不做 merge——merge 的半覆盖正是缩放事故同源病。
4. **诚实禁用**：requires 不满足=置灰+原因原文；永不静默隐藏、永不假跑。
5. **fail-loud**：manifest 缺失/形状错/provider 解析失败=启动即报，不猜不默认。
6. **一个真值**：同一 provider 服务 CLI/HTTP/首页/桌面四投影，不写第二份。
7. **基线双闸**：每 Phase 结束必过（R5 数字）；任何行为漂移=该 Phase 未完成。
8. **旧机制计数单调**：`audit_plugin_unification.py` 输出只许减少不许回涨。
9. **前端零构建**：投影产物=JSON+原生 ES module；不引 bundler（离线包结构不动）。
10. **既有四道 parity 门全绿**：插件化只改组织方式，不改物理与语义。
