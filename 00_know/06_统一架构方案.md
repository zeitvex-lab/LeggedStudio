## 0.4 四轴模型（2026-09-30 收敛，纲领）

**项目最终要做什么**：把「训一个足式机器人策略」从工程项目变成**流水线填表**——任何同族机型 × 任意技能组合，走完 训练→判据→浏览器/部署 全链，每步有 canary 自证（**五层保真链，2026-10-02 收齐**——移植性能损失只有五个通道，每层一道机器可查的门：

| 层 | 门 | 覆盖 |
|---|---|---|
| ① 本体（MJCF 物理） | `tools/mjcf_parity.py`：训练 MJCF vs 上游 spec 逐值 diff（质量/惯量/阻尼/臂架/几何） | **go2w 实证逐值一致**（18 体/16 关节/52 geom 全对齐）；部署侧 robot.xml 静态差 = intentional（生效层=契约 by_role，与上游运行期注入逐值同，浏览器/验收双端认契约 + H23 门禁） |
| ② 环境（装配） | `tools/golden_env_parity.py`：同一模型 × 双环境闭环对拍 | go2w legs-only Δ≤容差 ✓ |
| ③ 配方（奖惩/课程/命令/动作/终止） | `tools/recipe_parity.py` + `registry/reference_recipes/` | go2w legs-only 3→0 delta ✓ |
| ④ 管线（PPO/runner） | vendored 逐字同文 + 冒烟指纹（E8） | ✓ |
| ⑤ 测量（训练中/后） | `tools/trend_probe.py`（~250 轮趋势 / 50 轮平台判敛，结论随 Run 存证）+ `check_user_criteria.py` | 已流水线化 |

**为什么今天这么麻烦（根因诊断，2026-10-02）：契约是"被人推导的"，不是"被机器导出的"。**

今天修的每一刀（缩放 0.35、轮 35、观测错序、低通）共享同一个根因：**部署所需的全部信息
在训练时刻就已经存在**（effective-config 有动作段/缩放/模式/低通断点/命令域，env 自报表有
观测段序，ONNX 有宽度/关节名），但契约 historically 是"人/AI 读着这些产物手写的第二份文档"
——于是每个新机器人 × 新任务 = 重新做法证（我们这两天做的全部就是它），每一步都可能
静默错（没有门比对契约 vs 训练真值），且法证循环纯手工：训→摔→diff→找字段→修→再评。

**出路 = 契约导出原则：契约不是被写的，是被导出的。**

* `emit_deployment_contract(env, effective_config) -> contract_block`：**一个函数**在导出时刻
  机械产出部署契约全量（动作段表〔模式/缩放/关节/低通断点〕、观测段表〔env 自报序〕、
  命令域、物理常量）——覆盖全部行为字段，一次实现、一次测试，**之后任何机器人 × 任何任务
  免费获得正确契约**（取代 N 个事后打补丁的响应式 stamper——安全层泛化是半程，终点是导出）。
* 段表词汇表扩容（wheel/wrap 等语义进段数据）：观测布局从此**零 builder**——浏览器
  applyLayoutSpec 已消费同一数据；专用 builder 冻结不再新增。
* 之后 N 台机器人的边际成本 = MJCF + 形态契约 + 配方数据（族装配已要求的三样），
  **部署契约半边自动免费**；四道 parity 门自动验证，法证循环消失——因为不再有任何
  手工推导的环节。

**契约完备性原则（2026-10-02 用户问「所有都给还是可选项/契约如何确定/如何一套通行」的正式回答）**：

1. **对生效行为，契约必须给全——没有可选项**。"可选项"只存在于能力维（有无轮子/相机），
   不存在于完备维（用了的必须写全）。三条血的实证：action_scale 0.35/0.5、
   双段缩放（轮 35 速度模式被盖成 0.5 标量）、观测段序（快照部署视图 16 融合 ≠
   训练 8 段真序）——每一次都是"训练用了、契约没带、评测回落默认"。
2. **契约如何确定：单一来源 = run 的 effective-config + env 自报表**，promote 时机器
   盖章（不人填表）。已盖章：动作段缩放/模式（多段保险层）、PD/armature、布局 kind。
   待补：观测段序（信 env 自报表、不信快照部署视图）+ 动作低通断点（cut_off/control
   frequency）——都从 effective-config 提取。
3. **一套通行 = 同一 schema、逐机器人填数据、封闭性机器验证**：schema 字段全集固定
   （per-joint maps + 段表 + 数值域，机型无关）；**双向对拍门（assembly_parity，待建）**：
   effective-config ⊆ 契约 且 契约 ⊆ effective-config，任何 delta = 红（fail-closed）。
   这就是"填表可复现"的机器保证——今天全部事故（0.35/0.5、轮 35、观测错序、
   低通）都是这道门缺位的同一类病。

**「移植保持原性能 8–9 成乃至无损失」的可检验回答**：①–④ 全绿 ⇒ 移植语义**零偏差**（训出来的就是参考本身的行为，go2w legs-only 实证：对齐后行为复现上游、样本效率=上游自身水平〔此档上游官方口径 2 万轮〕）；⑤ 把『性能』变成数字（趋势格点 + 用户判据）。**推理侧零损失另有独立实证**：上游成品 5 产物在本框架全链 5/5。判负响应协议：⑤ 判负 ⇒ 回查 ③②①（顺序固定）⇒ 机制覆盖（参考内化）⇒ 最后才是参数，禁止加预算与参数狩猎。）

**统一框架 = 四条正交轴，技能是组合点**（不是代码模块）：

| 轴 | 载体 | 现状 |
|---|---|---|
| **机型** = 契约（PD/质量/关节序/缩放/命令范围——单一真值源） | `contract.json` | 8 机型 ✓ |
| **地形** = 课程档（plane/rough/stairs/obstacle_release/competition） | `registry/terrains/` | plane×8、rough×8 全族 ✓；stairs×1；**obstacle_release 轮足 ready 四足 missing** |
| **奖励** = 配方档（velocity/trot/jump/…，全部数据字段） | 族 Kit profile | 四足 10 技能 ✓；**轮足仅 velocity**；**保真门已立（2026-10-02）**：`tools/recipe_parity.py` vs `registry/reference_recipes/`——移植语义对拍一条命令，开训前出 delta（首拍 go2w legs-only 3→0） |
| **算法** = 变体（ppo/cts/him/amp/dreamwaq…） | variants 观测族 | ✓ |

**判据挂地形档，不挂技能**：速度类地形（plane/rough）→ 跟踪判据（check_user_criteria）；障碍类地形（obstacle_release/competition）→ 通过判据（validate_traversal_progress 半地块线，可升级为离散障碍通过率）。换了地形自动换判据——同一台机器同一策略在平地和障碍地用各自正确的尺子量。

**实测组合矩阵（2026-09-30）**：plane×8 机型、rough×8 机型——这两行就是"统一"的现实验证；stairs×1、obstacle_release×0（四足缺工厂）、轮足奖励轴 1/10——这些是轴上的洞。**判据挂地形档，不挂技能**：速度类地形（plane/rough）→ 跟踪判据（check_user_criteria）；障碍类地形（obstacle_release/competition）→ 通过判据（validate_traversal_progress 半地块线，可升级为离散障碍通过率）。换了地形自动换判据——同一台机器同一策略在平地和障碍地用各自正确的尺子量。

**任务插件层（在四轴之上，2026-09-30 用户定位修正补全）**：仿真的最大意义不只是验证策略——
是**把任务作为机器人的插件**：任务 = 机型 × 策略（四轴组合点）× 场景（scenario-contract：地图/
障碍/command_source/waypoints）× 控制器（follow/dwa/geometric/mpc）× 执行器（executors 装配），
**在基础仿真里组装运行**（浏览器 sim2sim + headless 双口径），跑通调通后再上实机——
**用仿真换实机调试时间**。基础仿真（够用即可）承载验证与任务运行；不需要高保真。
现状：场景契约/四控制器/DWA/导航闭环/执行器装配已在（backend 任务层全家），已支撑 e2e 到达率评测。

**收口路线 = 按轴补洞，不按机型补洞**：建四足 obstacle_release 课程工厂（一次补齐，四机型全可用）→ 轮足奖励轴扩档 → stairs 全族化。新参考进仓 = 取证后在轴上加一档；新机型进仓 = 写一份契约。

## 1. 三层参数分类（统一的基础）

统一的难点不在"要不要统一"，而在**把参数按"能不能统一"分成三层**——分错层，就会出现"统一了一个本该各自调的值"，或"各自维护了一个本该全仓一份的值"。

| 层 | 参数 | 归属（唯一真值在谁那） | 统一策略 |
|---|---|---|---|
| **硬物理** | 扭矩上限 / 速度上限 / 质量·惯量 / 关节限位 / 摩擦死区 / 电机带宽与延迟 | 契约 `contract.json` → 烘入 MJCF（datasheet / 系统辨识） | ❌ 不统一数值，**每包各自记录真值** |
| **半自主** | PD 增益（kp/kd）/ `action_scale` | 契约真值（物理约束下的**设计选择**） | ⚠️ 不统一数值，**统一"怎么选"**（起点公式 + 诊断表，见 §2.3） |
| **纯约定** | 关节序 / 观测组件顺序与命名与角色 / 命令源接口 / actor-critic 分组 / 算法接入接口 | **契约声明 + Kit 组装**（见 §2.2） | ✅ 全仓一份，且**必须可机验** |

**依据**：`04` §0.2–0.3（本体参数 vs 策略级参数先分家）；教程 Ch12「actuator 四层级」说明硬物理与半自主的边界，Ch05 §5.5 说明 `action_scale` 为何是设计选择而非硬件常量。

**为什么半自主层只统一"怎么选"**：同一台机器人在不同策略下 `action_scale` 取值不同（`04` §0.3 已实证 go1 有 0.25 与逐关节两种）——写进机器人契约必然与某一个策略冲突；但"怎么选"可以被公式与诊断表固定下来。

### 2.2 纯约定的**真实载体**（这一节是 v1.0 的主要勘误点）

纯约定**不是**写在 Kit 文档里的口头约定，而是**声明在契约、由 Kit 与前端各取一份消费**：

| 约定 | 真实载体（唯一真值） | 消费方 |
|---|---|---|
| **关节序** | `contract.json → action.joint_order`（有序数组） | 训练（配方装配）/ 部署（解码层）/ 浏览器（`browser-config`） |
| **关节命名** | ⚠️ **保留上游物理原名**（如 go2 `FL_hip_joint / FL_thigh_joint / FL_calf_joint`）——**本仓不做逻辑改名**（上游对照需要原名） | 全链 |
| **模型序 → 契约序的重排** | `action.reindex_from_model`（**仅 m20 / g1 两个包声明**，其余包两序一致） | 训练与部署 |
| **观测组件（顺序 + 角色 + 历史 + 可部署性）** | `contract.json → observation.components[]`，字段 `name / width / source / role / history / deployment_available`，外加 `observation.dimension` 汇总 | 训练（obs 组装）/ 浏览器（JS 镜像）/ 部署（D0 核对）/ ONNX metadata 校验 |
| **actor / critic 分组** | 同上，`components[].role`（`actor` / `critic`） | 非对称 AC 装配 |
| **控制频率** | `contract.json → control.{control_hz, physics_hz, decimation}` | 训练 / 浏览器 / 部署三端同源 |
| **命令源** | 任务配置按任务类型提供（速度命令 / 参考动作帧 / 无外部命令）；导航侧 planner 命令源见 `05` H3；运行时限值在 `registry/{motion_commands,cameras,arrival_criteria}.json` | 训练 / 高级仿真 |
| **算法接入接口** | `AlgorithmPlugin` 协议（`adapters/mjlab/algorithms/base.py`）+ 注册表 | 训练 worker |

**勘误（v1.0 → v2.0，均已实测核对）**：

1. v1.0 写"每包契约一份 `joint_logical_map`，onboard 时自动推断"——**全仓不存在该字段**；重排走的是 `action.reindex_from_model`。
2. v1.0 写"逻辑关节命名统一为 `hip_abduction / hip_pitch / knee / wheel`"——**与代码相悖**：契约与 MJCF 用的是上游原名；改名的代价是丢失上游对照能力（`03` §4 的字段级对账就靠原名）。
3. v1.0 写"观测固定槽位公式 `3+3+cmd+2N+W+N`"——**方向对、归属错**：槽位是**契约声明**（`observation.components`）的结果，不是 Kit 里的硬编码公式。go2 实测 6 组件 `3+3+3+12+12+12 = 45`，`dimension: 45`，全部 `deployment_available: true`。
4. v1.0 把控制频率当作统一项——**实测不是**：12 包为 `50/200/decimation=4`；go2 与 zex-w 为 `50/500/decimation=10`；`wuji_hand` 为 `20/100/decimation=5`。频率属"每包真值"，不属约定。

**两套观测真值的边界**：本仓 Kit 口径 45 维（`3+3+3+12+12+12`，不含 `base_lin_vel`）与 mjlab 官方 actor 形态 48 维（`3+3+3+3+12+12+12`，含 `base_lin_vel`）**并存且各自自洽**——已在 `05` §1.2「诚实边界」登记，新增机型时必须核对用的是哪一套（门禁：`tools/audit_observation_contract.py`、`tools/audit_policy_obs_width.py`）。

> **依据**：教程 Ch05 §5.2「原则二：可部署性——actor 只能看到真机可得的信号」（`base_lin_vel` 在真机上需状态估计，故属特权/可选）与 §5.4「Actor/Critic 非对称」；Ch13 §13.2 的 48/72 维对照。

### 2.3 半自主参数的"怎么选"（统一的是方法，不是数值）

**`action_scale` 的起点与诊断**（教程 Ch05 §5.5）：

```text
processed_action = raw_action × scale + offset      # raw 无量纲，offset 缺省 = default_joint_pos
起点：scale ≈ 关节行程 / 2~4（行程 = joint_limit 上界 − 下界）
```

| 观测现象 | `scale` 可能问题 | 第一检查项 |
|---|---|---|
| zero agent 姿态不合理 | offset 错 | `default_joint_pos` |
| random agent 立即炸飞 | scale 太大或 clip 缺失 | processed action 范围 |
| 策略动作长期贴边 | scale 太小 | raw action 分布 |
| 关节频繁撞限位 | scale 太大或 offset 偏移 | `dof_pos_limits` 惩罚量级 |
| 行为很保守 | scale 太小或 entropy 太低 | action std |
| 高频抖动 | scale 大或动作惩罚弱 | `action_rate` 量级 |

**落点**：数值住 `contract.json → action.action_scale`（`04` §0.3 定为**策略级参数**，不进机器人契约的本体部分）；诊断表住 Kit；工作台提供可视化（`05` D10 动作缩放卡片）。

**PD 增益的起点与边界**（教程 Ch12 §12.2 工程实战 + §12.1 四层级）：

```text
kp 初值 ≈ 0.6 × τ_max / 0.1        # 让 0.1 rad 位置误差产生 ~60% 峰值力矩
kd 初值 ≈ 2 × sqrt(kp × J)         # 临界阻尼
forcerange 取"持续扭矩"（≈ 峰值 30–50%），不是 datasheet 峰值
```

**两条硬边界**（都已在代码侧成立，这里只声明原则）：

- **PD 数值住 MJCF**：`contract.json → actuator_profile` 经 `tools/bake_mjcf_physics.py` 烘入 `model/*.xml`，MJCF 是**执行真值**（`02` §12；`tools/validate_mjcf_contract.py` 守门）。
- **MuJoCo 的阻尼会叠加**：`<position kv>` 与 `<joint damping>` 相加（Ch12 §12.2），跨端对齐时必须合计——这正是 `tools/audit_sim2sim_consistency.py`（H23）在守的东西。

### 2.4 新机器人移植流程（DoD 第 2 条的落地形态）

```text
onboard（1 目录 + 模型）
  → 契约生成器（推断关节序/限位/执行器角色 + 建议 action_scale）
  → 人确认/微调 → 契约真值 + MJCF 定稿
  → profile 复用 Kit 模板（只改关节表 / 地形偏好 / 算法选择）
  → verify（对账门禁）→ 冒烟（小档）→ 长训（新规模）
```

**验收**：`onboard → verify → train → export` 全绿且**不改 Python**；两入口（Web 向导 / CLI）产出同一 `package_id`（`05` I3 + I1 已达成，测试钉住）。

> **依据**：教程 Ch22（DIY 从零注册任务；smoke → zero → random 三步验证；10 类环境 bug 中"照搬他机 reward/scale"排第一）；`02` §3 判据。

### 2.5 算法插件层（"算法像插件一样可插拔"）

**目标**：任意算法（现有 + UniLab 级 + 未来新增）**不改训练链**即可接入。

| 件 | 落点 | 现状（实测 2026-09-19） |
|---|---|---|
| 插件协议 | `adapters/mjlab/algorithms/base.py`（`AlgorithmPlugin` + `verify_plugin`，fail-closed） | ✅ |
| 插件注册表 | `adapters/mjlab/algorithms/registry.json`（schema `algorithm-plugin-registry-1.0`） | ✅ 7 插件：`cts / dreamwaq / amp / distill / him / hora / appo`，每项含 `module / plugin_class / variants / legacy_entrypoints / metadata`（上游出处与许可随插件走） |
| 注册表加载与解析 | `algorithms/plugin_registry.py`（`load_registry` / `list_plugins` / `resolve_plugin` / `bind_algorithm_to_runner_cfg`） | ✅ 控制面（无 torch）只读 JSON；训练面才 import 插件类；元数据与类属性漂移即报错 |
| 插件目录 | `algorithms/<algo>/`（算法类 + 模型 + 配置 schema） | ✅ go2 四族（cts/dreamwaq/amp/distill）已迁入，`local_tasks` 留薄 re-export |
| profile 选择算法 | profile 里 `algorithm`（人读标签）+ **`algorithm_plugin`（插件名）** | ✅ 2026-10-04 刷新：**8 个 profile** 带声明（cts 系 b2/go2 三档 + him + m20-dreamwaq + go2-dreamwaq + go2-amp-dreamwaq；amp 变体随 source_amp 上移已可用） |

**必须知道的口径（不写出来就会误导下一个人）**：

- **词汇表已合并为一份**（2026-09-19）：`algorithms/registry.py` 的 `list_algorithms()` 现在**从插件注册表派生**（内置 runner 算法 + 7 插件），`ALGORITHM_REGISTRY` 那张独立的表已删除；标签解析走 `resolve_algorithm()`（未登记即 fail-closed，消息里同时列出两套名字）。
- **"三个能"必须分清**：`registered`（在词汇表里）→ `native_supported`（能接进 mjlab native runner）→ **`product_open`（产品内可创建训练）**。今天只有 PPO 是 `product_open`；插件是"协议就绪、绑定已接线、未经真训练验证"，API 对此回 **501 并说明是哪一类原因**（不再是"反正不是 PPO"）。
- **绑定已接线**：`plugin_registry.apply_algorithm_plugin()` + `adapters/mjlab/native_worker.py` —— **只在 profile 显式声明 `algorithm_plugin` 时生效**（52 个 profile 里 50 个一行不碰），绑定结果（插件名 / 变体 / class_name）进 run 报告，产物谱系可查。
- **切换算法的正确写法**是 `algorithm: "HIM"`（人读标签）+ `algorithm_plugin: "him"`（插件名）；v1.0 的"`algorithm: "him"` 一行即可"不准确。profile 实测还有 `TS` / `CTS/TS` / `HIM` 等历史标签，只有带 `algorithm_plugin` 的两个指向明确。

**上游取用**：UniLab algos（`03` §1 ③ `unilab_new`）作为新算法主源，接入前按 `03` §8.2 准入顺序评估；许可与出处随插件元数据走（`registry/licenses.json` 对账）。

## 3. 统一仿真架构

### 3.1 基础仿真（数据链）

```
输入：assets/robots/<id>/simulation/config.json（策略声明：policy_id / 路径 / 摘要）
  → GET /api/simulation/browser-config/<robot>  下发

  → MuJoCo WASM（vendor 本地、零 CDN、可离线）做物理
  → ONNX Runtime Web 做推理

  • 观测按契约 observation.components 顺序组装（web/sim2sim/obs/ 是同一份逻辑的 JS 镜像）
  • 关节序按 action.joint_order（与训练一致 ⇒ 部署零映射）
```

| **内容摘要口径**（一个工件一个哈希） | `contracts/validator.py`（`normalized_sha256` 单文件 / `package_digest` 多文件） | ①单文件摘要有 **3 份**逐字相同的实现（`contracts` / `pack_catalog` / `generate_packs`），靠注释"两侧必须同步修改"维系；②`project_api._tree_hash` **少了归一**，与 `model_api` 写进 `robot_package.json` **同一字段**的值必不相同（实测本仓 4 个包全不同）；③`file_digest`（分块 + 原始字节）与 B40 已收口的归一口径在**同一模块**并存 | `contracts/tests/test_content_digest_single_source.py`（单/多文件、目录口径、**AST 源码级扫描**：对文件字节的 `sha256` 只许一处） |

**分层边界**：定位规则共用，**域特有前置留在各自域** —— 浏览器要求包内有 MJCF 模型（`browser_package` 里 404），部署要求契约真值存在（`deploy_pack` 里 fail-closed）。前置不同是设计，不是漂移；把它塞进共用定位才会让"为什么这台机器浏览器能开、部署导不出"重新变得无法回答。

**内容摘要的取舍必须知道（2026-09-19 实测）**：归一（CRLF → LF）是为了"同一份工件在 Windows 与 CI 只有一个哈希"，但对**二进制**它是有损的 —— 实测本仓 **50 个 onnx 全部**含 `0D 0A` 字节对（MB 级二进制几乎必然出现），所以归一**会改变**二进制的哈希，也意味着 `0D 0A ↔ 0A` 的改动无法被检出。这是有意的取舍（跨机可复现优先于二进制完整性最强），**不是**可以顺手改掉的口径；要改就得连 `policies/index.json` 一起重签（`build_all(write=True)`）。

**前端共享实现的边界（2026-09-19，这是否决理由不是缺口）**：`web/shared/api.js` 只服务**普通脚本页**（三个训练页 / workbench / 其余独立页）。`web/sim2sim/**` 是 ES module 世界，**刻意不接入**它：

* 离线包（`backend/bundle_export.py`）以 `web/sim2sim/` 为**根**打包（`_player_static_files()` 的相对路径就是按这个根算的），包内根本没有"上一级"——`app.js` 里写 `import "../shared/api.js"` 在离线包里必然 404；
* 要接入就得先把离线包的目录结构改成"`web/` 布局"，那是一次**动离线形态**的改造；
* 换来的是什么？sim2sim 那 6 处 JSON 调用**已经检查 `res.ok`**（它们是 6 个文件里做得最规范的一组），接进去只多一个**超时**。

代价（动离线）远大于收益（一处超时），所以选择不动 —— 真要解决 sim2sim 的超时，应在其内部加（或等离线包结构改造时一并接入）。它另外 8 处 fetch 读的是字节/文本（wasm、ONNX、CSV、图片、地形 XML），本就不适用 JSON 封装。

## 4. 统一部署架构

### 4.1 部署包（`backend/deploy_pack.py → generate_deploy_package()` 实测产物）

```
deploy_package/（zip）
├── deployment-contract.yaml    ← 人读投影：关节映射 / 控制频率 / PD / armature / 限位
├── deployment_contract.json    ← 机器读 payload（deployment-contract-1.0）
├── deployment_contract.py      ← 同 payload 的 Python 常量形态（生成头标明真值源）
├── fsm_safety_template.py      ← 安全状态机骨架（PASSIVE→STAND→POLICY→RECOVER→ESTOP）
├── action_decoder_template.py  ← 逻辑序 → 真实电机命令（含 decode() 与 single_joint_sine_test()）
├── platform_adapter.py         ← 目标平台适配层（unitree_sdk2 / ros2 / 通用骨架）
├── 人工确认清单.md              ← 增益降 50% / 急停 / 零点 / 软限位
└── （可选）d2_bench_test.py     ← 台架扫频模板（bench_mode 才生成）
```

**三条边界**：

- **唯一实现**：`POST /api/deploy/package` 与 CLI `deploy pack` 都调同一个 `generate_deploy_package`，不各自再写一套打包逻辑（CLI 只换落点：`--out`）。
- **默认不含策略权重**：要随包携带需显式给策略路径；**给了而文件不存在必须报错**（fail-closed——"以为带上了策略"比不带更危险）。**已收口（2026-09-19）**：携带逻辑下沉进 `generate_deploy_package(policy_onnx=...)` 单一实现，API（`POST /api/deploy/package`）与 CLI（`deploy package --policy`）同源；输入校验全部前置于产出——失败时连输出目录都不建（"失败留半个包"比没包更难查）。
- **gate 判据单一实现**：`deploy_gate_report()` 是唯一实现，`GET /api/deploy/gate/<id>` 与 CLI `deploy gate` 只做"异常 → HTTP / 退出码"的映射，不再各自比较字段。
- **一键生成 ≠ 一键上机**：包内带人工确认清单与劣化档（`degraded`：力矩 ×0.8），对应 `01` §9 的 3C 原则。

### 4.2 部署链路

```text
训练 → ONNX 导出（产物自证：ONNX 实测宽度为准）→ 评测达标（没有报告不放行）
  → deploy gate（DENYLIST fail-closed：硬约束字段不一致即 deny）
  → 部署包生成（契约投影 + 安全状态机 + 解码层 + 确认清单）
  → 人工确认清单逐项确认 → 实机
```

`deploy gate` 的判据与打包**同源**：CLI `deploy gate <robot>` 与 `GET /api/deploy/gate/{robot_id}` 都走 `backend/export_gate.compare_contracts`（包内 `contract.json` vs `contract_legacy_v2.json`），存在 blocker 即退出码 1，可直接当上机前门禁。

## 14. 目标架构：一切即插件

### 14.1 一页图

```
  registry/plugin-registry.json                ← 唯一装配清单（6 套旧机制的全集收敛点）
        │ ①加载 ②schema 校验 ③拓扑排序（requires 驱动，不写死 boot 顺序）
        ▼
  plugins/runtime.py（内核，≤400 行，零业务零机型 id）
        ├─ 服务上下文：ctx.provide(key, value) / ctx.get(key) / ctx.try_get(key)
        ├─ 事件五模式：emit / waterfall / parallel / serial / bail
        └─ patch：按 id 整行替换或插入（不 merge——防半覆盖静默漂移）
        │
        ├─ 消费投影①产品面：面板导航 / HTTP 端点 / CLI 子命令 / 桌面可见性（四投影）
        ├─ 消费投影②装配面：族 Kit / 技能 / 地形 / 奖励 / 算法（训练 worker 侧）
        ├─ 消费投影③验证面：插件自带 verify → 门禁事件（30 个 audit 脚本归位）
        └─ 消费投影④生态面：第三方包过 manifest 校验进索引（"包即插件"）
```

### 14.2 内核三原语（cordis 语义 / Python 实现，文件 `plugins/runtime.py`）

| 原语 | API | dsh 对应 | 本仓适配说明 |
|---|---|---|---|
| **服务上下文** | `ctx.provide(key, value) -> disposer`；`ctx.get(key)`（缺即抛，列出可用）；`ctx.try_get(key)` | `ctx.<key>` 服务声明 + `inject` | **装载顺序由 requires 可用性驱动（拓扑排序）**，取代 6 处手写 boot 顺序；注册即 effect，`ctx.dispose()` 逆序回滚 |
| **事件** | `ctx.on(event, fn)` / `ctx.emit|waterfall|parallel|serial|bail(event, ...)` | 5 dispatch modes | emit=观察；waterfall=中间件（契约完备性封口这类横切）；bail=首票否决（部署 gate）；**不引 fiber/async**（训练装配一次性同步，异步无意义——否决理由） |
| **patch** | `apply_patch(base, patch)`：id 命中=**整行替换**，未命中=插入，后写胜 | bundle/profile/patch 三层 | 层叠来源：插件基线→族→机型包→档案→CLI；**整行替换而非 merge 是有意取舍**（dsh 原注释：merge 产生"半覆盖"，正是本仓 0.35/0.5 缩放事故的同一类病） |

**内核硬约束**：≤400 行；不 import 本仓任何模块；不出现机型/族/功能 id（门禁 `test_kernel_purity.py` AST 扫描）。现 `plugins/core.py` 的 Seam 桶升级为服务上下文，`Entry` 保留为装载行单元。

### 14.4 四投影：面板插件的真实形态

迁移后一个"页面/面板"声明带来四份产物，全部由 `plugin-registry` 生成、**零手写路由/导航**：

| 导航 | topnav/侧栏/桌面 launcher 的导航数组（JSON 下发） | `web/shared/topnav.js` 手写清单 + `panel_registry.render_navigation` |
| HTTP | FastAPI 路由（从 `surfaces.http` 挂载，provider 走真 `module:attr` importlib） | `api_complete.py` 的 31 条内联路由中可归属单域的部分 |
| CLI | argparse 子命令表 | `cli_panels.py` 的 `globals().get` 假解析 |
| 桌面 | `desktop.visible` 过滤 + capability 裁剪 | electron launcher 静态清单 |

**诚实禁用**：`requires.services`（如 backend/训练栈/GPU）探测不可用 → 置灰+原因原文，永不静默隐藏。

### 14.5 双侧投影纪律（与"控制面永不 import 训练栈"的和解）

dsh 是单进程 TS 无此问题；本仓必须显式设计：

- **`impl.control_plane`**：零 torch 可 import（加载、校验、投影、目录）——**门禁**：`test_impl_importability.py` 在无训练栈环境 import 全部 control_plane provider；
- **`impl.runtime`**：只在 worker 子进程 import（env cfg / 算法类 / 评测器）；
- 两份 impl 由**同一个 `plugin.json` 声明**——协议唯一，投影两侧（这是与"6 套机制"的根本区别：dsh 的 `packages/api` 声明与 `packages/extensions` 实现分离思想的 Python 版）。

### 14.6 验证器事件化（30 个 audit/validate 归位）

- 插件声明 `verify[]`，`tools/audit_plugin_verify.py` 扫描全部 manifest 生成门禁清单（**新增能力=加插件，不改 CI 脚本清单**——dsh "Where new behavior goes" 表的本仓等价物）；
- 现有 30 个脚本**不重写**，只改发现方式：从"手维护在 .cnb.yml"改为"从 manifest 派生"；
- 全站级横切（doc_reality_check、obs_crosscheck 全量）保留为**内核事件**（waterfall 模式）。

### 14.7 seam 图（机器生成，进 CI）

`tools/gen_capability_seams.py` 从 manifest 生成 `docs/capability-seams.md` 等价物：每个 seam 的提供者/消费者/覆盖矩阵 + **"新增一个 X 该挂哪"表**。这是"框架零特判"从 grep 纪律升级为**机器可查结构**的门。

## 15. 技术方案选择：四个候选与否决理由

| 候选 | 内容 | 否决/采纳理由 |
|---|---|---|
| **A** | vendor Cordis（TS 插件框架），前端/桌面全迁 TS + pnpm | **否决**：① web/ 是无构建纯静态（136 文件）且离线包以 `web/sim2sim/` 为根——迁构建链=动离线形态，§3.1 已裁决不动；② backend 是 Python 控制面，cordis 的 ctx 服务模型无法跨语言；③ 迁移成本 >> 收益（协议语义可抄，技术栈不可抄） |
| **B ★** | **单一插件协议**：cordis 语义 + Python 实现（§14.2 三原语），registry/ 收敛为 `plugin.json`，13 seam | **采纳**：① 保留 web 无构建与四层隔离两条既有裁决；② 死内核 `plugins/core.py` 升级即用，不推翻；③ 与 `adapters/mjlab` 隔离 venv 兼容（双侧投影 §14.5） |

| **D** | 照搬 dsh monorepo tier 物理重排（packages/* + bundles/* + apps/*） | **否决**：① 路径硬依赖极重（doc_reality_check 16 锚点、registry evidence 字段路径、包 stub 沿目录自举、测试 docstring 行号引用）；② tier 是**逻辑概念**（内核/域插件/组合层/投影），物理路径不搬家也能成立——用 manifest 表达 tier，不用目录表达 |

| 维度 | 选择 | 依据 |
|---|---|---|
| 内核语言 | Python（`plugins/runtime.py` ≤400 行） | 控制面同语言；训练面已是 Python |

## 18. 不变式与门禁（全 Phase 有效）

1. **控制面永不 import 训练栈**：`impl.control_plane` 全量在无 torch 环境 import 成功（`test_impl_importability.py`）——插件化不得破坏四层隔离。
2. **内核 ≤400 行零业务**：AST 门禁，机型/族/功能 id 出现即红。
3. **patch 整行替换**：不做 merge——merge 的半覆盖正是缩放事故同源病。
4. **诚实禁用**：requires 不满足=置灰+原因原文；永不静默隐藏、永不假跑。
5. **fail-loud**：manifest 缺失/形状错/provider 解析失败=启动即报，不猜不默认。
6. **一个真值**：同一 provider 服务 CLI/HTTP/首页/桌面四投影，不写第二份。
7. **基线双闸**：每 Phase 结束必过（R5 数字）；任何行为漂移=该 Phase 未完成。
8. **旧机制计数单调**：`audit_plugin_unification.py` 输出只许减少不许回涨。
9. **前端零构建**：投影产物=JSON+原生 ES module；不引 bundler（离线包结构不动）。
10. **既有四道 parity 门全绿**：插件化只改组织方式，不改物理与语义。

## 21. 维护规则

1. **只写"统一什么 / 不统一什么 / 为什么"**：定位与边界进 `01`，阶段与模块路径进 `02`，上游依据进 `03`，参数取值进 `04`，状态进 `05`。
2. **每张表都要有可核对的载体**：写"统一"必须给**文件或字段**，不给就是口号；写"现状"必须给路径或命令。
3. **不写会漂的数字**：插件数、包内 `.py` 数、进度等一律标实测日期与命令，长期真值指向 `05` §0 锚点与门禁输出。
4. **Kit 层新增能力先问"属于哪个形态"**：答不上来就不进 Kit；形态归类以 `05` P 组头的表为准（m20 归轮足、g1 归人形）。
5. **冻结包不参与 Kit 迁移**：`wuji_hand` / `microduck` / `tron1_pf/sf/wf` 维持现状。
6. **半自主参数两处不混**：起点公式与诊断表住 Kit，具体数值住契约——两处不互相抄。
7. **改动要留否决理由**：重要选型变更除"选了什么、为什么"，还要写"**为什么不选 B/C/D**"。
8. **本文改动需同步 `05`** 的 P 组架构描述（`05` 已在 P 组头引用本文）。

**取舍顺序（同一需求内部，排期用）**：`可追溯 > 契约 > 分层隔离 > 差异数据化 > 单一事实源 > 只读版本化 > 减法 > 证据等级 > 零命令行`（原 `00_项目价值观.md` 已删除，只保留顺序；出处见 `02` §15）。

   "声明了的算法从未被训练层验证"这类缝隙已封。
2. **`--repeat N` 间歇故障门禁**：一次绿不算绿；任何一次非 ok 即判 `flaky`。
   源起：warp 层时间窗式间歇 CUDA 故障（见下条）一次通过无法排除。
3. **runner 工厂禁写死包内私有算法类名**（`backend/test_runner_classname_rule.py` AST 全源树扫描）：
   算法类名只许 `mjlab.*`（框架默认）或 `adapters.mjlab.algorithms.*`（注册插件），
   由 profile 的 `algorithm_plugin` 声明在装配期覆写；包内私有算法扩展（`<pkg>.mdp.rl:*`）判红。
   附：AMP 源口径实现已上移 `adapters/mjlab/algorithms/amp/source_amp.py`（跨族可用），
   族 Kit imitation 薄 re-export；豁免清单清零。

另：**训练前 GPU 环境健康检查**——`validate_training_smoke` 起跑前检测 GPU 上驻留的
VM/hypervisor 类进程（MuMu/VirtualBox 等，启发式进程名匹配），命中打印 `[env!]` 警告并写入报告
`env_warnings`：其显存/调度压力会产生**时间窗式**间歇 CUDA 故障（代码无关、红绿成簇），
实证案例 m20-dreamwaq（2026-10-04，MuMu 驻留期 ~50% 红、关闭后稳定绿）。

## 追记（2026-10-05）：第四条工程规则——完训≠达标（completion 判据钩子）

4. **档案声明了验收判据就在训练终态后自动出判定**：launcher `finalize` 在
   `train_completed` 终态后检查 profile 的 `criteria.tracking` 声明（`training_config.json`
