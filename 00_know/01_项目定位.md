## 一、机会与问题定义

腿足机器人从业者要的根本结果，是一台能稳定运行、表现可信的机器狗。这个结果通向一条有明确工序的链路：改模型与参数、训出策略、验证表现、送上实机。今天这条链路的每一道工序都有人做——环境供应、训练框架、仿真器、部署模板都不缺，但**工序之间没有路**：环境要自己配，同一份物理参数要在几处对齐，验证靠人记得去做。

最硬的障碍不在算法，在**门槛**。一套能跑的训练栈要跨过系统、驱动、CUDA、框架、依赖版本，以及"这份配置对着哪个模型"这几道关；任何一道对不上，人就停在工作开始之前。第二道障碍在**改动**：调一个参数要改代码，换一台机器人要复制一份工程，于是只有会写代码的人能参与。第三道障碍在**交接**：约定在每一步传递中都可能被悄悄换掉，它不报错，只让结果慢慢变差——同一份策略换个环境、换台机器、改一个参数结果就不同，而没人能说清是哪一步变的。

三层障碍对应三层机会。先把门槛做成产品能力，让"想验证一个想法"和"能跑起来"之间的距离从几天压到几分钟。再把改动变成数据，让机器人、任务、奖励、参数都可点选、可替换，非专业出身的人才能真正进入这条链路。最后把交接留下证据，让每一步的产物都带来龙去脉、结论可复核。前两层决定"用不用"，第三层决定"信不信"。

三层做透之后，还有一个更大的机会会自己浮现：当配置、资产、结论都以同一种形态存在，它们就能被分享、被复用、被第三方扩展——工具因此有机会从一套内部脚本长成生态。

## 二、目标用户与核心需求

按「离代码的距离」分三层，而不是按身份分。

**不写代码的使用者**（学生、爱好者、机器人队、其他方向的工程师）：手上有一份改好的模型或配置，要的是导入就能训、训完就能看到机器狗跑起来，判据是不碰终端。**写代码但不写训练的工程师**（机器人实验室）：有模型和实机，缺训练栈与验证流程，要的是"我的模型进去、经过验证的策略出来"。**写训练的研究者**：要让论文方法真正跑通并能横向比较，要的是每次实验自带来源、可复核、可对比。

还有一类人决定生态能不能成立：**贡献者**（方法作者、竞赛队、上游项目的移植者）——把上游方法、资产、机型做成一个包发出来的人。对他们，打包要便宜、校验要透明、许可与出处要清楚，否则没人愿意往里放东西。

需求因此是三条，正好对应第一节的三层障碍：**进得来**（门槛由产品承担，不因环境、依赖、参数而卡住）、**改得动**（差异用数据表达，换机型换任务不写代码）、**走得完**（每一步都有可交接的产物，任何一次结果都能说清它从哪来、和上一次差在哪）。

> 这三条是**排期与取舍时的第一依据**（怎么用见 [`02_项目规划.md`](./02_项目规划.md) §1 与 §11）。

## 三、产品定位与价值主张

定位一句话：一款把腿足机器人**从模型到实机的整条链路收进一个产品**的桌面 + 浏览器工作台——改参数、训策略、验表现、送上去，使用者不需要懂命令行。

它的价值主张按用户拆开。对不写代码的人，是把"没跑过强化学习"变成"导入配置、点开始、看机器狗跑"。对工程师，是把环境、依赖与拼接排查的成本从人身上移到产品里。对研究者，是让每一次实验都自带来龙去脉，结论可以复核、可以横向比较。对贡献者，是把改好的东西打成一个包，别人导入即可跑。

它和现有做法的差别，不在功能多少，而在三个坚持。第一，**门槛由产品承担**：零命令行是产品能力，不是可选体验。第二，**差异由数据表达**：换构型、换任务只新增一份配置，而不是复制一份工程。第三，**交接必须可检查**：约定对不上的产物要被拒绝，而不是被放行。

## 四、产品形态：桌面程序、Web 与 CLI

产品对外呈现为三种形态，但**后端是唯一的能力中心**，三者都只是它的客户端，共用同一份接口契约。三种形态各自承担第一节里的一条承诺：桌面承担"门槛由产品承担"，Web 承担"界面与仿真对所有人可用"（含把别人发出来的东西导进来跑），CLI 承担"交接可检查、可自动化"。

**桌面程序**是"门槛由产品承担"这条承诺所在，也是零命令行唯一成立的地方。它负责运行时的供应、**环境配置与设置**、后台服务的生命周期，以及和操作系统的集成。用户双击打开，点配置、点启动，其余都由程序自己完成。这是唯一能为用户提供"开箱即用"的形态。

**Web 工作台**是全部业务界面的家，也把浏览器仿真装了进来。它不做算力密集的工作，只负责呈现状态与传递操作。它既能被桌面程序打开，也能在后台运行时被浏览器直接访问，因此同一套界面既能服务本机单人使用，也能服务团队内的共享部署；导入别人改好的机器人包、技能包与策略包，走的也是这里。

**CLI** 是给自动化与持续集成准备的工程师入口。它和 Web 共用同一份契约，是同一能力的另一个入口，而不是另一套产品。

分工到能力一级是这样的——同一份能力只由一个形态提供，其余形态只做入口：

| 能力 | 提供方 | 入口 |
|---|---|---|
| 运行时供应 / 环境配置与设置 / 后端生命周期 / 系统集成 | 桌面形态 | 桌面程序 |
| 界面、配置编辑、任务监控、部署向导 | Web 工作台 | Web |
| 浏览器仿真 | Web 工作台（数据由后端提供） | Web |
| 训练 / 评估 / 服务端仿真 / 打包 | 后端（隔离执行） | Web 或 CLI |
| 自动化与持续集成 | 后端接口 | CLI |

两条容易混的边界。**其一，打开方式**：Web 既能被桌面程序打开，也能在后端运行时用浏览器直接打开，"零命令行"这条承诺只在桌面形态成立。**其二，文件来源**：后端在本机时资源可以直接按路径引用，后端在远端时同一份资源只能上传，所以来源统一抽象成"路径或上传"，而不是两套逻辑。

## 五、技术选型：每一项目标靠什么实现

技术选型服务于产品目标。每一项选型都要能回答"它服务上面哪一条需求（进得来 / 改得动 / 走得完）"，答不上来就不进这份文档。这里只说"选了什么、为什么"，不展开实现。

**一键配置环境用"固定版本 + 隔离运行时 + 镜像与离线双通道"（服务"进得来"）。** 门槛的解法不是让用户去装环境，而是把环境搬进产品：启动器只读，点"配置"才下载一份固定版本的 Python 与 CUDA 运行时，装进用户数据目录、与系统环境互不干扰，各训练后端各自锁死自己的运行环境、互不污染。下载源分档位（国内镜像 / 官方 / 自定义 / 离线），离线可走本地 wheelhouse；镜像失败自动回退官方，并把这次回退如实报出来——"不联网"是硬保证，不是礼貌请求。

**训练框架选 mjlab（服务"走得完"）。** 腿足机器人的强化学习依赖大规模并行仿真来采样，训练效率直接决定"从想法到结果"要多久。mjlab 是基于 MuJoCo 的 GPU 向量化训练框架，是当前的主框架。框架被设计成可插拔，后期可以按同一份清单接入 UniLab 或 IsaacLab，各后端用各自隔离的运行环境，互不污染。

**物理仿真选 MuJoCo（服务"进得来"与"走得完"）。** 它是腿足动力学仿真的事实标准，接触与关节建模成熟。服务端用它做高保真仿真；浏览器端则用它的 WebAssembly 版本，让仿真在用户浏览器里本地运行，零安装、可离线——"进得来"有一半是它给的。同一个仿真内核，既在服务端跑，也在浏览器里跑。

**策略用 ONNX 作为中间格式（服务"走得完"）。** 训练产出的策略统一导出为 ONNX，于是一份策略既能在浏览器里直接用，也能进入部署链路，不需要为不同端各训一份。

**契约为单一事实源（服务"改得动"）。** 机器人、任务、感知的差异全部沉到一份 JSON Schema 契约里。前端表单、配置校验、训练配置树都由这份契约驱动，前后端字段因此不会漂移。新增一台机器人或一个任务，只是新增一份配置，而不是复制一份工程。

**内容模型是五份一等资源加一个组合层（服务"走得完"与"改得动"）。** 形态、技能、参考动作、场景、策略各是一等资源，各有一份独立演进的 schema，组合靠引用而不是拷贝；组合层只做引用组合，并带四个阶段的质量门（验证 / 训练 / 仿真 / 部署）。资源里不放代码，算法实现归各自的后端，差异全部下沉为数据。

**一切皆可插件（服务"改得动"，同时是生态的入场方式）。** 机器人、任务、感知、部署目标都是插件包，第三方包经过校验才进入索引。这让"换构型、换任务像换插件"成为产品的默认体验，也让别人发出来的东西有地方进来。

## 六、北极星体验与核心旅程

北极星体验是：**一个新人，从打开到让机器狗动起来，用时很短，且结果可回放**。这里的"可回放"不是演示，而是判断——同一份结果重复两次，应当一致。能回放，才算真的跑通。

同一条体验还有另一半：**跑不起来的时候，判断不是"失败"，而是"挂在哪一层"**。门槛能不能被信任，取决于它说得清自己挂在哪里，而不是让人回去翻日志。

围绕这条体验，四类用户各有自己的旅程。新手走"装完、配置、启动、选资产、看机器狗动起来"，全程不碰终端。玩家走"导入模型、换任务、换感知，像换插件一样切换"。研究者走"打开一次训练的完整档案，把配置、依赖、种子、评测与上一次并排对比"。贡献者走"把我的机器人或任务打成包发出去，别人导入即可跑"——这条旅程检验的是打包到底便不便宜。四条旅程共享同一个底座，只是在不同深度上使用它。

## 七、商业与竞争思路

它本质是一款**工具型产品**，靠"把链路做顺、把结论做可信"建立价值。它的壁垒不在某个单点功能，而在**谱系与工作流的锁定**：当用户的实验、资产、结论都沉淀在同一条可追溯的链路里，迁移成本会自然升高。

生态转起来之后，还会叠加第二层壁垒：别人发出来的包越多，产品对下一个人越有用。但这层网络效应只在不牺牲可信的前提下成立——进索引要过校验，许可与出处要随包一起走；宁可少一个包，也不多一个说不清来源的包。

竞争上，它不与通用仿真平台拼覆盖，也不与训练框架拼算法。它切的是"从模型到实机"这条具体链路，把别人当工具用的东西，做成一条完整、低门槛、可复核、可被第三方扩展的流水线。

## 八、边界与主要风险

它不会成为通用机器人平台，也不做机械臂或整条产线。它不是云端训练服务，默认形态在用户本机运行；远端使用是被允许的，但不与本地共用同一套安全假设。它不替代成熟的导航与控制生态，只做对接与登记，不重复造轮子。它也不退化成"脚本加配置"的集合——零命令行是它的核心差异，不是可选项。

主要风险有四类，需要提前看住。**范围蔓延**：腿足之外的需求很诱人，但一旦放开边界，"专而透"就会变成"全而浅"。**验证失真**：仿真里的好结果不等于实机上的好结果，这条落差必须被显式管理，而不是默认忽略。**复杂度回潮**：每加一个能力，门槛就有回升的风险，需要持续把复杂度压回后台。**供给冷启动**：打包不够便宜、校验不够透明，生态就只是一句口号——供给侧的成本要和需求侧的门槛一样，被当成产品指标来看。

边界还要对外说得清：哪些能力已经能被证明、哪些当前不能声称，另有单一清单维护（见 [`05_任务清单.md`](./05_任务清单.md) 的"已具备的可验证能力"与"诚实边界"两节），这一节只写原则，不复制那份清单。

## 九、3C / 软硬结合的特殊考量

这是一款横跨软件与硬件的产品，因此有几条 3C 特有的原则。第一，**仿真到实机的落差是常态**，产品要把"验证"和"部署"分开看，不能用仿真结论直接替代实机结论。第二，**硬件依赖要前置管理**，运行环境、驱动、设备差异都要被显式建模，而不是在出错时才被发现。第三，**交付要有明确的验收口径**，每一次上机都要有"怎么算合格"的判定，而不是"先装上再说"。第四，**许可与出处随资产走**：机型、动作、上游代码的许可各不相同，产品要把许可链当成资产的一部分随包传递，而不是在分发时才想起来。

## 十、一句话收束

它不是"又一套训练工具"，而是把腿足机器人**从模型到实机的整条链路收进一个产品**：门槛由产品承担，差异由数据表达，每一段的交接都留下证据。做成它靠三件事——让不写代码的人也能进得来，让改动不必改代码，让每一步的结论都能复核；这三条立住之后，才有资格谈生态。

对不写代码的人，它是"装完就能让机器狗跑起来"的入口；对工程师，它是一条省掉拼接与排查的产线；对研究者，它是一台每一步都可复核的台架；对贡献者，它是一个把东西发出去别人就能用的地方。
