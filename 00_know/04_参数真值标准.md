# 机器人参数真值标准

> **一句话**：机器人参数**只确定一套** —— 不允许多个位置叠加维护，不允许"两边都写错就一直错"。调试时只需看一个地方，改了必然生效。
> **三件事定了标准**：① 每个参数**只有一个家** ② 取值**以多源共识为准** ③ **本体参数与策略级参数先分家**。

## 0. 规则（四条）

### 0.1 一个参数只有一个家

1. **一个参数只有一个家**：标准是 `assets/robots/<pkg>/contract.json`。
2. 其它位置只允许两种身份，且**不得独立维护**：
   - **派生视图**：由真值计算得到（如 `locomotion_type` ← `morphology`）；
   - **兼容投影**：给 v2/旧消费方读取的形状（如 `urdf.mass_source` ← `morphology.mass_source`）。
3. **声明值必须等于派生值**，由测试守护（漂移即失败），而不是靠人工对账。

### 0.2 选值规则（`R0`–`R3` 按序判定，命中即停）

| # | 规则 | 说明 |
|---|---|---|
| **R-P** | **项目级裁决：哪个参考项目有"训练 + 部署"全链路，就用哪套**；候选都具备时，取覆盖环节更多、任务更复杂者 | **最高优先级**（用户裁定），先选项目、再看参数 |
| **R1** | **训练 ∩ 部署 一致 ⇒ 直接采用** | 两层独立来源给出同一个值，置信度最高 |
| **R2** | 否则，**模型层（URDF/MJCF/xacro）∩ 其一一致 ⇒ 采用** | 物理描述是硬件事实，优先于任何一方的手调值 |
| **R3** | 否则，**参数更全且任务更复杂的一方** | 例如 mjlab（带 `armature`/`velocity_limit`、含 tricks/aerial 等复杂任务）优于单任务的平坦行走配置 |
| **R0** | 本体参数 vs 策略级参数**先分家** | 同机型不同策略取值不同的参数（`action_scale`、`rl_kp/rl_kd`）**根本不进机器人契约** |

### 0.3 本体参数 vs 策略级参数（先分家）

**判据**：一个参数如果在不同策略下取值不同，它就**不是**机器人参数，写进机器人契约必然与某一个策略冲突。

| 类别 | 含义 | 归属 | 典型参数 |
|---|---|---|---|
| **本体参数** | 只由硬件决定，与任务/策略无关 | 机器人契约 `actuator_profile` / `joints` / `control` | `effort_limit`、`armature`、`velocity_limit`、PD 基准 `stiffness`/`damping`、`default_pose`、控制频率 |
| **策略级参数** | 同机型不同策略取不同值 | 策略契约 `policies[].contract`（部署包 yaml 的那套） | `action_scale`（0.25 / 0.5 / 逐关节）、**策略专用增益** `rl_kp` / `rl_kd`、obs scales |

**实证**：同一台 go1 —— `himloco` 用 `rl_kp=40`，`go1`/`moe` 用 `rl_kp=20`；`action_scale` 有 0.25（go1/himloco/moe）与逐关节 `[0.125,0.25,0.25]×4`（np3o）两种。⇒ 二者均**非本体属性**，不得写成机器人常量。

**由此消解的一个真实陷阱**：部署 yaml 里 `fixed_kp/fixed_kd`（站桩控制器）与 `rl_kp/rl_kd`（策略）是**两套增益**并存，此前若一并当作"机器人增益"就会互相覆盖。

### 0.4 多源共识法（2026-09-13 定为标准）

> **裁决**：参数取值**以多源共识为准** —— 官方源与多份独立实现一致的那个值即标准；只有单一来源有、或不同版本给出不同值时，判为"版本差异"，**登记不改**；任何来源都没有则不猜。

**判据**（方法详见 [`05_任务清单.md`](./05_任务清单.md) §方法固化）：① 官方 + 多份非官方**一致** → 我方错，改我方；② **单一来源 / 版本差异** → 登记；③ **全无** → 记缺口或按官方写明公式推导。**每个数值都要落到源码路径**。

**已按此裁决的机型：go2w（2026-09-13）**

| 源 | 类型 | hip/thigh kp/kd/effort | calf kp/kd/effort | wheel kd/effort |
|---|---|---|---|---|
| `unitree_rl_mjlab/.../unitree_go2w/go2w_constants.py` | **官方** mjlab | 20 / 0.5 / 23.5 | 20 / 0.5 / 35.5 | 0.5 / 23.5 |
| `robot_lab/.../assets/unitree.py`（`fan_robotlab` 同） | IsaacLab | 25 / 0.5 / 23.5 | 并入 legs | 0 / 0.5 / 23.5 |
| `unilab_new/UniLab/.../go2w.yaml` + test cfg | UniLab | 未声明 kp/kd；leg_action_scale 0.25→0.5 | — | wheel_kd **0.5** |
| `unitree_rl_mjlab_go2w/mjlab/asset_zoo/.../go2w_constants.py` | fork（**我方原训练源**） | 20 / **1.0** / 23.5 | **40 / 2.0 / 45.0** | **2.0 / 45.0** |
| 官方 MJCF `unitree_mujoco/unitree_robots/go2w/go2w.xml` | MJCF | ctrlrange 23.7 | ctrlrange **45.43** | ctrlrange **15** |

**结论（已落盘）**：hip/thigh `20 / 0.5 / 23.5`、calf `20 / 0.5 / 35.5`、wheel `0.5 / 23.5 / armature 0.01`；契约 + MJCF + **训练源 `go2w_constants.py`** 三处同步。官方 MJCF 的 `45.43 / 15` 登记为**真机包络参考**（不改动力学）。
**代价**：既有 go2w 策略是按 fork 那套（40/2.0/45）训的 → 若要继续用它们，需**重训**才与新口径对齐（验收会显式暴露差异，不静默）。

## 1. 概念：这些参数是什么

**`stiffness` / `damping`** —— 位置伺服的 PD 增益：
- `stiffness`（kp）= 把**位置误差**换成力矩的比例项，单位 N·m/rad；
- `damping`（kd）= 把**速度误差**换成力矩的微分项，单位 N·m·s/rad。

仿真里 `τ = kp·(q* − q) − kd·q̇ + τ_ff`。它们**不全是手调参数**：mjlab 由硬件常数推导（`k = I_reflected·ω_n²`、`d = 2ζ·I_reflected·ω_n`，转子惯量×减速比²＋期望自然频率），所以在本项目里它们**属于本体属性**；而部署 yaml 里那套 `rl_kp/rl_kd` 是**策略层覆盖**。

**摩擦损耗（`friction_loss`）** —— 即 MJCF 的 `dof_frictionloss`：关节的**库仑干摩擦**（恒定阻力矩、方向恒与运动方向相反，单位 N·m），补偿减速箱/轴承的摩擦死区。不建模的话关节会"过于顺滑"，表现为轻轻一推就转。浏览器仿真直接改写 `model.dof_frictionloss`（`web/sim2sim/app.js` 的 `applyJointPhysicsConstants`）。
> 这一项已由 B3 补齐：8 包全部显式声明，来源分 A（模型编译即有，幂等）/ B（模型为 0 但参考项目非零）/ C（双方皆无，显式化）三组。

## 2. 真值链三层 + 各文件的角色

### 2.1 真值链（三层，各有其家）

| 层 | 家 | 谁读 | 一致性由谁守 |
|---|---|---|---|
| **本体参数**（与任务无关） | 契约 `actuator_profile` / `joints` / `control` | 训练、验收、浏览器（无策略卡时） | `contracts/tests` + `tools/check_control_consistency.py` |
| **策略级参数**（同机型不同策略不同值） | `simulation/config.json` 的 `policies[].contract` | **浏览器运行时**（卡覆盖包级） | §0.3 的分工原则；**验收侧尚未跟随**（见 `05_任务清单.md` 待决） |
| **执行真值** | `model/robot.xml`（MJCF） | 验收 / 训练装配 / 浏览器（编译后） | `tools/bake_mjcf_physics.py --check` + `tools/validate_mjcf_contract.py` |

> **判据**：一个参数如果在不同策略下取值不同（§0.3 已给实证：go1 的 `rl_kp` 40 vs 20），它就**不能**写进机器人契约当唯一值 —— 这正是"验收必须按被验收策略的卡取参"的原因。

### 2.2 各文件的角色

| 文件 | 角色 | 是否机器人参数的"家" |
|---|---|---|
| `contract.json` | **标准**：构型、角色、执行器、动作、观测、控制 | ✅ **唯一**（= 包默认口径） |
| **`simulation/config.json` 的 `policies[].contract`** | **策略级覆盖**：同一机型不同策略取不同值（`rl_kp`/`rl_kd`/`action_scale`） | ⚠️ **运行时真值** —— 浏览器 payload 的 contract = 包级 `policy_contract` **+ 被选中策略卡覆盖**（`backend/simulation_api.py:430-437`） |
| **`model/robot.xml`（MJCF）** | **执行真值**：`<option>` / 逐关节 `armature`·`frictionloss` / `<actuator>` 已被契约固化 | ⚠️ 执行侧的家（由 `tools/bake_mjcf_physics.py` 写入、`tools/validate_mjcf_contract.py` 守门） |
| `contract_legacy_v2.json`（v2 视图） | 兼容快照：URDF 路径/hash/**总质量**、关节限位、观测组件名 | ⚠️ 仅这些"数据类"字段；语义字段一律由 `contract.json` 覆盖 |
| `simulation/config.json` | 未迁移包的**兼容回落**（标记 `source="legacy_config"`） | ❌ 不再参与取值 |
| `robot_package.json` | 打包元数据（capabilities / 目录布局 / demo_policies） | ❌ 非机器人参数 |
| `packs/*.pack.json` | 资源组合**纯引用** + `sha256` | ❌ 引用，不拷贝内容 |

### 4.7 go1 / go2 / g1 三方对照（深挖结论）

**结论速览**：
1. **没有"唯一正确的一套"** —— 同一个参数在部署包、训练栈之间存在**系统性分歧**，因为职责不同：**部署包（带 `.pt`）**给的是**某个策略实际用的值**（含手调增益）；**mjlab 契约**给的是**由执行器常数推导的物理值**（带 `armature`/`velocity_limit`）；**legged_gym / mujoco_playground / unilab** 又各自有一套 task 默认。
2. 我们仓库事实上各选了一套，但**选择依据不统一**（go1 跟部署包、go2 跟 LLoco、g1 跟 mjlab 推导），**且没把"选了哪套、为什么"写下来** —— 这才是"多套叠加"的根源：**不是数据错，而是没有声明标准**。
3. 本文档即为该声明。

## 6.1 接触参数：口径＝训练域（2026-09-14 裁决，**已定**）

**背景**：接触参数此前**从未进过本文的真值链** —— 它随包内 MJCF 继承自上游训练工程，既不在契约（契约只有关节侧 `friction_loss`），也没做过 R0–R3 选值。因此 `03` §4.1 里写的"go2 **37 处**摩擦差异"是**误导性计数**：37 只是**继承 default 的几何个数**，真正的决策点只有两处：

| 决策点 | 我方 | 官方（`unitree_mujoco@1eb6642`） | 说明 |
|---|---|---|---|
| default `<geom friction>` | `0.6` | `0.4` | `0.6` 是 legged_gym 系训练工程惯例（`Dreamwaq` / `him_dog` / `HIMLoco` / `gym_ex` 实测同值） |
| 足端 geom | 显式 `contype=1 conaffinity=2` | `<geom name="FL" class="foot"/>`（只给 class → 继承 `1/1`） | 我方显式抬高了足端亲和性 |
| 足端 `friction` | `0.4 0.02 0.01` | `0.4 0.02 0.01` | **本来就一致** |
| `condim` / `priority` / `margin` | 同 | 同 | — |

**裁决**：接触参数按**「训练域」口径**管理，**不按物理事实**。

1. **理由**：真机地面摩擦**不是常数**（不同地表差数倍），它天然是**域随机化对象**；对它追求"唯一真值"没有物理依据。
2. **归属**：**数值真源＝包内 MJCF 一处**；契约**不复制数值**（抄进契约就成第二份真值，V2 不允许）。
3. **契约侧只做声明**：8 包 `contract.json` 的 `physics_domain.contact`（`authority: training_domain` + 官方对照来源 + 说明）——它**不参与** `bake_mjcf_physics` 固化，也**不属于**物理真值唯一性门禁（实测 `bake --check` 0 待固化、`validate_mjcf_contract` 0 漂移）。
4. **官方值定位为「对照参考」**，不是"正确答案"。
5. 后续做域随机化时，直接随机化这一层即可（与 `m20_dreamwaq/mdp/randomization.py` 的逐 dof 写法同源思路）。
