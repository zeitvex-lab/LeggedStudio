# B2 报告：契约单轨 —— `locomotion_type` 收敛为 v3 morphology 的派生视图

> **日期**：2026-09-10 ｜ **范围**：14 个内置包的 `locomotion_type` × v2/v3 双写

## 1. 问题：两个枚举描述同一件事，且会互相漂移

| 版本 | 字段 | 表达能力 |
|---|---|---|
| v2 | `locomotion_type`：`P` 四足点足 / `B` 双足 / `W` 轮足 / `H` 手 | **粗**——无法区分"双足 + 足底 + 踝"与"双足点足" |
| v3 | `morphology`：`id` / `legs` / `leg_pattern` / `foot_type` / `actuator_type` | **细**——可表达上述组合 |

两者长期并存并**互相漂移**。实测全量表：

| 机型 | v3.loco | v2.loco | legs | 构型 id | foot_type | 判定 |
|---|---|---|---|---|---|---|
| `deeprobotics_lite3` | P | P | 4 | quadruped_12dof | point | ✓ |
| `deeprobotics_m20` | W | W | 4 | wheel_leg_16dof | wheel | ✓ |
| `limx_tron1_pf` | B | B | 2 | biped | point | ✓ |
| `limx_tron1_sf` | B | B | 2 | biped | **sole** | ✓ |
| `limx_tron1_wf` | W | W | 2 | wheel_foot_biped | wheel | ✓ |
| **`microduck`** | **P** | **P** | **2** | **biped** | **sole** | ✗ **漂移** |
| `unitree_b2` / `b2w` | P / W | P / W | 4 | quadruped / wheel_leg | point / wheel | ✓ |
| `unitree_g1` | B | B | 2 | humanoid | sole | ✓ |
| `unitree_go1` / `go2` / `go2w` | P / P / W | 同 | 4 | quadruped / wheel_leg | point / wheel | ✓ |
| `wuji_hand` | H | H | 1 | hand | — | ✓ |
| `zex-w` | W | W | 4 | wheel_leg_16dof | wheel | ✓ |

**`microduck` 是唯一例外，且两侧同时写错**：它是 `legs=2` 的双足、`foot_type=sole`、
带踝关节，与 `limx_tron1_sf` 完全同构（后者正确写着 `B`）；它却写 `P`（=四足点足），
与自身构型直接矛盾。这正是"两边都写错就一直错"的典型——**靠人工对账发现不了**。

## 2. 收敛规则（按"保留表达能力更强的一方"）

* **v3 `morphology` 是唯一真值**——它能表达 v2 枚举表达不了的组合；
* `locomotion_type` 退化为**派生视图**，由 morphology 计算，不再单独维护 ⇒ 结构上不可能再漂移。

派生优先级：

1. `morphology.id == "hand"`（或无足端、`legs <= 1`）→ `H`
2. `foot_type == "wheel"` 或 `leg_pattern` 含 `wheel` → `W`
3. `legs == 2` → `B`
4. 其余 → `P`
5. **无 `morphology` 的旧契约不猜**：沿用其存量值，缺失才回落 `P`

注意第 3 条与 `foot_type` 无关：`sole` 不改变双足判定（`tron1_sf` 即 `B` + `sole`）——
该枚举描述**运动形态**而非足端材质，这也是"用更细的 v3 表达、粗枚举只做投影"的理由。

## 3. 落地

| 位置 | 改动 |
|---|---|
| `contracts/locomotion_view.py` | **新增** `locomotion_type_from_contract()`：唯一派生入口（含退化行为与完整理由） |
| `contracts/contract_loader.py` | `merge_v3_over_v2()` 不再采信任何一侧的存量 `locomotion_type`，改用派生值 |
| `assets/robots/microduck/contract_v3.json` | `P` → `B`（与派生值一致） |
| `assets/robots/microduck/contract.json` | `P` → `B`（同上；该文件用双空格对齐） |
| `contracts/tests/test_locomotion_view.py` | **新增**漂移守护（6 个用例） |

## 4. 为什么这次修复是安全的

`tools/generate_asset_inventory.py` 的上游分类学映射是：

```24:30:tools/generate_asset_inventory.py
# locomotion_type in contract.json -> contracts Locomotion enum value.
_LOCOMOTION = {
    "P": "point_foot",   # point-foot quadruped / biped
    "B": "point_foot",   # biped
    "W": "wheeled_leg",  # wheel-leg
    "H": None,           # hand: not a locomotion candidate
}
```

**`P` 与 `B` 都映射到 `point_foot`**，所以 `microduck` 的 `P`→`B` 对上游分类学与
`QUADRUPED_ASSET_INVENTORY.json` **零影响**；改变的只是"它被正确描述为双足"，
以及"存量与派生不再漂移"。

## 5. 漂移 CI（本里程碑的核心产出）

`LocomotionViewTest` 断言：

1. 14 包的派生值与期望表逐条一致；
2. 派生值必须是合法枚举（`P/B/W/H`）；
3. **存量值（v3 与 v2 两侧）都必须等于派生值** ← 真正的漂移守护；
4. 合并后契约（训练侧唯一读取口）给出派生值；
5. 无 `morphology` 的旧契约沿用存量值（不猜）；
6. `H` / `W` 优先于腿数判定（双足轮足仍是 `W`，灵巧手仍是 `H`）。
